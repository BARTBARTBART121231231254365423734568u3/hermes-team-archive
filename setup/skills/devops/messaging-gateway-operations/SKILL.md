# Messaging Gateway Operations

Configure and repair remote messaging control surfaces without confusing adapter health, reactions, or service state with a working conversation.

## Procedure

1. **Map the transport before changing it.** Identify the single credential owner, multiplexed profiles, configured allowlists, home channel, and the live service process. Keep one coordinator-facing bot identity per platform; specialists stay behind the coordinator and Kanban. Before dispatching repair, confirm the assignee profile resolves the required messaging skills with `hermes -p <assignee> skills list` — profile skills are materialized copies under `~/.hermes/profiles/<assignee>/skills/`, so copy any missing canonical skill from `~/.hermes/skills/` into the profile first, otherwise the worker starts without its operating procedure.
2. **Capture a real failing message with its channel.** Ask for one short message in the intended private conversation plus the channel/server name (a wider screenshot showing the channel header), then correlate its timestamp with gateway logs. A reaction or typing indicator proves only that the adapter observed the event; require evidence that authorization passed, an agent turn started, and a reply was delivered.
3. **Trace authorization in the runtime scope.** In multiplex mode, distinguish process-global environment, profile secret scope, platform `extra` configuration, and adapter-owned policy. Compare the observed sender/chat identity with the value read by the exact authorization layer, without printing tokens or private IDs. Query narrow fields or redact output before displaying a broad CLI status report, because diagnostic summaries can include credential previews unrelated to the investigation.
4. **Write policy to the authoritative scope.** Preserve a private allowlist and disabled allow-all flags. When authorization uses profile-scoped secret reads, ensure the allowlist exists in that profile scope; a top-level compatibility key can look correct to the CLI while remaining invisible to the live gate. Keep the canonical platform configuration in sync so setup/status commands also report truth.
5. **Reload once after the cause is fixed.** Do not restart repeatedly while testing hypotheses. Restart only after configuration readback or a regression test proves the authoritative input is correct. For a blocked code release, read its existing checkpoint/manifest before re-diagnosing — the pending step (symlink switch, config, or restart) is usually already recorded there, and log-diving first wastes the window. Long-lived gateway processes hold configuration in memory, so fallback-chain and allowlist edits take effect only after the restart — verify post-restart logs, not the config file alone. A gateway-child worker must not restart its own service: the worker dies mid-task and may strand the board claim. Before assigning an operator, compare the operator shell's `/proc/self/cgroup` with the gateway MainPID's `/proc/<pid>/cgroup`; a separate cgroup establishes survival of the restart but never substitutes for explicit approval, worker drain, or the release guard. For a rollout that requires stopping the gateway and changing source/config, prepare an externally run, fail-closed operator script that verifies the exact approved revision, zero productive workers, a fresh private restore-checked backup, service identity and rollback path; dry-run it first. Pin the approved candidate SHA, checkout and previous runtime independently of any editable release manifest, then fail closed on a jointly shifted manifest/checkout; a self-consistent but unauthorized manifest can otherwise pass. Enumerate the authorization grants actually read by the adapter across YAML, effective profile settings, process/secret environment, bots and pairing ledgers, and exercise negative probes for each independent grant before an operator runs the release; checking only one allowlist or a similarly named environment flag can miss a bypass. Agree on the execution window and operator before the user leaves: if Thomas cannot be at SSH, an approved operator outside the gateway service cgroup may run the dry-run-verified procedure after all workers drain; never hand an interactive confirmation prompt to a gateway-child worker. Read back the new PID, loaded revision, effective policy and transport before declaring success. Resolve live code through the install symlink, not the restart alone: read back the symlink target and its HEAD SHA against the reviewed SHA, because a restart reloads whatever the symlink still points at — retarget it to the reviewed worktree before restarting for a code release. Never give a bare stop command that can leave Hermes offline before deployment/start. After ANY guarded restart failure, independently read the service ActiveState and MainPID immediately; a script reporting `gateway failed to stop` may have left systemd in `failed` with MainPID=0. If stopped with no workers and the approved source/config remain intact, start the existing service and read back active state, new PID, source revision and configured policy before further debugging. Do not rerun the same operator script until its stop-state guard is corrected and dry-run. If tool approval is withdrawn because the Desktop client cannot display it, stop agent-side attempts; do not rephrase the denied command or schedule a deferred subprocess around it. Inspect the user's actual Desktop update UI before proposing a fix: a command-center **backend update** changes the server and is not a client-only repair; do not invent a separate Desktop update control when none is visible. With explicit human consent, prepare and dry-run a fail-closed, exact-revision operator procedure, then execute it from Thomas's authenticated SSH terminal or an independently approved operator outside the gateway cgroup; do not convert a denied approval into an alternate execution path. Keep the gateway restart and rollback inside that single guarded procedure; never ask him to stop the gateway by itself, since that could sever the chat before recovery. Verify the new process, loaded revision, bounded policy, and actual user-facing transport before reporting completion.
6. **Verify both directions separately.** Confirm a real inbound message is accepted, the agent uses live task/system state, and the outbound reply appears in the same intended conversation. Service health, a websocket connection, slash-command synchronization, or an outbound test message alone is insufficient.
7. **Separate chat from operations noise.** Use a dedicated home/updates channel for gateway starting, restarting, shutdown, and online notices. Keep the conversational channel for user requests and agent answers. If the runtime also notifies active sessions, add a focused routing rule: when Discord has a distinct home channel, send lifecycle notices only there; preserve active-chat fallback when no home exists and deduplicate when both targets are the same.
8. **Run interactive pairing on the surface the user requested.** For WhatsApp linked-device setup, prefer the Hermes dashboard’s Messaging → WhatsApp onboarding flow when Thomas asks to see the QR in the dashboard; it exposes the native onboarding API and renders the QR for scanning. Do not substitute the gateway listener root or leave a terminal pairing process running behind a dashboard flow. If terminal pairing was already started, terminate it before starting dashboard onboarding so only one session owns the QR. Inspect the rendered login page before giving sign-in advice: a dashboard basic-auth form expects its configured username/password, not an email identity. Read back and provide only the non-secret username; if the password is unknown, offer a supported reset rather than guessing, exposing stored credentials, or repeatedly attempting login.
9. **Gate only the irreducible human action.** Agents may select the agreed bot/self-chat mode and prepare the Thomas-only allowlist, but Thomas must choose/provide the real account and scan the linked-device QR. Explain that boundary before launching an interactive command; never surprise him with a prompt or ask him to paste a phone number into an ordinary shell where it can execute as a command.
10. **Verify external writes by readback.** After creating a channel, changing routing, posting a test notice, or deleting/moving bot-owned messages, fetch the exact channel/config target and assert the resulting name, parent, content, and absence/presence conditions.
11. **Report only the finished product.** For Thomas, suppress narrated diagnostics and intermediate attempts. Return a short final statement naming what now works and where messages will appear; surface only a blocker that requires his action.

## Diagnostic decision points

- **Reaction but no reply:** inspect authorization logs first; do not blame the model or response channel until an agent turn is proven.
- **Typing forever:** correlate with the gateway log and running turn. Typing can start before central authorization or survive a failed turn, so it is not acceptance evidence.
- **CLI says allowed but runtime rejects:** inspect multiplex profile scope and platform adapter configuration; do not keep rewriting the same top-level key.
- **Journal says explicitly disabled but the default profile reads enabled:** inspect every specialist profile's `platforms.<x>.enabled` — a stale per-profile `enabled: false` pin shadows the coordinator and wins over environment credentials, and the warning names only `config.yaml` without saying which layer set it.
- **Restart succeeded but behavior is unchanged:** compare the install symlink target and its HEAD SHA with the reviewed SHA before touching config — the restart reloaded the old checkout, so retarget the symlink to the reviewed worktree, then restart once and verify.
- **Runtime status stamps connected but the journal shows the explicit-disable path:** resolve which profile owns the live adapter before declaring health — a secondary profile's adapter on a different credential can stamp `connected` while the default coordinator's adapter never started, so compare credential presence per profile scope (lengths/hashes only) and the writer PID.
- **Allowlist looks set but the owner is still unauthorized:** compare the configured ID against the gateway-observed sender ID character-by-character — a single trailing-digit typo drops every inbound while length checks still look plausible, so require exact string equality.
- **Connected but zero inbound lines around the user's timestamp:** read both the file log and the live service journal and compare the file mtime — the file log can stall while the journal holds live lines, so absence in one source never proves absence.
- **User mentions visible but no inbound or denial logged:** verify the live channel against the allowed-channels and free-response channel configuration — server-channel messages outside the listened set can drop silently before the authorization layer logs. An empty channel allowlist fails closed per-message while the fail-closed warning logs only once per process — later drops leave no trace, so always verify the connect-time allowlist snapshot, not just the current config.
- **Repeated restart/online notices in the chat channel:** treat as a restart loop starving inbound processing and as proof home-channel routing is not applied — fix the loop and the routing before touching the allowlist.
- **Discord slash sync is rate-limited:** treat it as a separate control-plane condition. Verify ordinary message transport independently, and disable unnecessary resync only through the supported policy when existing commands need not change.
- **Lifecycle notice appears in chat:** setting a home channel may route startup messages but not active-session shutdown notices. Verify both paths with a focused test and a real planned restart.
- **Dashboard URL shows Not Found:** the gateway listener is not the web dashboard. Start or locate the Hermes dashboard and open its actual dashboard port, then use Messaging → WhatsApp rather than guessing a route on the webhook listener.
- **WhatsApp QR is visible only in terminal:** stop that pairing process before launching dashboard onboarding; simultaneous pairing sessions rotate or contend for the same linked-device state.

## Safety gates

- Never enable allow-all as a shortcut.
- Never paste bot tokens, QR payloads, phone numbers, or private IDs into task cards, reports, commits, or chat.
- Bind remote approvals to a specific request, user, chat, action, profile, and expiry; generic affirmative text must not authorize work.
- Preserve one credential owner per platform under a multiplexed gateway; duplicate profile credentials create ambiguous ownership and parked adapters.
