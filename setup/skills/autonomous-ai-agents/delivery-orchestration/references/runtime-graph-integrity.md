# Runtime and graph integrity

## Verify active execution

- Prove that work is active before reporting it: require a `running` card, current run id/PID, and recent heartbeat. A `ready` card or provider-usage meter is not execution evidence.
- Record meaningful transitions on the board as they occur: actual start, implementation commit, verification result, reviewer verdict, correction start, and deployment start/completion. Inspect automatic Kanban notices and act internally without replying in the initiating chat when Thomas has requested silence there; contact him only for a concrete decision or help he must provide. Do not turn a tool-only board check into a repeated “no help needed” chat acknowledgment.
- Keep project-specific conversations strictly scoped to that project. Ignore unrelated cards shown in assignee history, and consolidate malformed duplicate notifications into the one authoritative lane and blocker the user needs.
- When ready work is not being claimed, verify gateway/dispatcher health. Restart the installed gateway only when it is actually down, then read back gateway status and claimed cards before saying work resumed.
- To prove a two-worker runtime cap, create finite disposable cards in distinct repositories/worktrees, then link both as parents of the coordinating card and dependency-block that coordinator so its own claim does not consume a global worker slot. Read the claim/completion events for distinct run IDs, PIDs, sessions, and overlapping intervals; a third queued card must claim only after a slot frees. For same-checkout exclusion, run a read-only holder and follower assigned the same existing directory without an artificial dependency between them, then compare holder completion against follower claim. Resume the coordinator after the probes complete; do not infer isolation from passing tests or merely queued cards.
- For runtime-cap rollback, inspect whether the dispatcher reads settings at boot before treating an on-disk config change as live. Drain workers, take and restore-check a fresh operations backup, then use the operator-approved restart path and verify the new gateway PID, installed SHA, and boot-loaded cap. Only then launch finite read-only holder/follower probes; compare the holder completion event with the follower claim event and inspect claim-lock PIDs against the gateway or other dispatchers before calling it live-gateway proof. A follower claimed later by a separate dispatcher supports ordering but does not by itself prove the gateway enforced the cap. Restore the intended cap through the same drained, guarded restart and repeat live admission verification.
- When an operator is launched from a gateway-hosted chat, run it as an independently scoped transient user-systemd service, not an in-gateway subprocess: stopping the gateway terminates its cgroup. Preflight an inert transient unit and inspect its distinct cgroup. Preserve authorization, bounded productive-worker drain, fail-closed board inventory, fresh restore-checked backup, post-backup recheck, and recovery; an outer subprocess timeout can kill rollback midway through stop/config/start. Sequence a replacement after a prior operator exits and check its result before a second restart; never race operators or circumvent a denied in-gateway stop command.
- Distinguish dormant gateway-owned execute-code kernels from productive workers when draining: permit only expected direct gateway-owned runners blocked in `pipe_read`, and reject active or unknown children. Recheck before stop and in recovery. Inspect named-board database layouts before backup and locking; fail closed if any board is not covered. After restart, verify the report, new PID, code and config, then launch fresh real-dispatcher jobs and inspect separate run IDs, claim-lock PIDs, overlap, commits/tests and natural receipts. A restarted service or two `running` rows is not complete acceptance.
- For an exact-origin receipt, create a finite read-only completion probe from the initiating conversation with native Kanban, verify its subscription target, then require the completion notification to actually arrive in that same conversation. A `done` card, `subscribed:true`, or notifier log alone is not delivery proof; keep unrelated telemetry gates open.
- Before creating project-pinned probes from a specialist, resolve the fixture slug and ID in that creator's profile registry and read back each card's `project_id`, worktree kind, and path before admission; profile-local project records can silently turn an unresolved project into scratch. Retire malformed cards before their parent releases them. Start any read-only external telemetry monitor in its own user-systemd cgroup; check active PID and a fresh first sample before releasing workers, and size its bounded runtime for queue delay plus execution. If the monitor expires while probes remain gated, restart and verify it before admission. Call frequency-bound RSS maxima *sampled*, not absolute peaks.
- For a controlled disposable worker crash, prepare a fresh initially gated probe and a one-shot external operator before admission. Require independent security approval of the exact operator bytes **before** sharing an executable command with Thomas. Bind every signaling entry point—including internal monitor modes—to the same interactive authorization and one-shot token; pin the approved script digest and require clean exact source/fixture revisions. Test the **actual CLI entrypoint** non-destructively for operator→monitor token consumption and replay refusal, not just imported helper functions: a top-level used-marker check can accidentally reject the authorized monitor after the operator creates the marker. Install the independently approved digest as a private file, read back its mode and hash, and run the real dry-run only after all workers drain; a dry run that refused before approval or while a worker was active does not prove the operator is ready. Guard the exact task/run/PID/start ticks, process ancestry, gateway claim lock, workspace and other checkout users, and signal through a process-identity-pinned primitive such as Linux pidfd rather than a numeric PID recheck (which races reuse). Model dependency wait from the board's actual status and unmet parents: a coordinator may be `todo` while waiting, not `blocked`. If any guard or tool approval fails, send no signal, leave the card gated, and record an unforced attempt rather than a reclaim pass. Before giving an operator a one-shot command, exercise every pre-signal state mutation through the installed API against an isolated real SQLite board—not just mocked CLI or helper tests. In particular, construct the connection with the row shape expected by that API and verify a genuinely blocked card transitions correctly; a post-confirmation exception can consume the one-shot marker without admitting the worker. If live execution fails after authorization, inspect the marker, monitor unit, card/run events, and gateway before considering any retry; never reset or reuse a consumed one-shot token, and require a fresh card/token plus exact-byte review and renewed consent for another destructive attempt. Never reroute a denied destructive command through another profile or execution surface to evade approval.

## Route by effective capability

1. List required operations: local file/source inspection, read-only database queries, process checks, web retrieval, and artifact writing as applicable. Inspect relevant toolset fields only; do not dump credentials or whole configurations.
2. Check both base toolsets and launch-platform overrides, plus required skill availability. A profile's chat permissions do not prove dispatched CLI capability. Confirm tools actually exposed in the worker run before treating configuration as proof.
3. On a capability block, read the card/run evidence and compare candidate profiles before retrying. Prefer rerouting the original card to an equipped profile over duplicating it or broadening privileges; a stronger model cannot supply missing tools.
4. For a blocked inactive card, run `hermes kanban --board <board> reassign <task-id> <profile> --reason <reason>`, preserve scope and origin in a comment, unblock the same card, and read it back. Resolve active claims first if a worker still owns it.
5. Distinguish routing recovery from execution recovery. Reassignment and ready status prove only queue placement; require a new run and actual capability evidence before claiming the blocker is resolved.

## Preserve task contracts

- Read every created card back before dispatch. If the stored body contains `[truncated]` or omits acceptance criteria, add one compact `FULL CONTRACT` comment immediately.
- Bind reviews to the stored exact SHA and acceptance contract, never an assumed branch tip.
- Before a completed preview/publisher card releases rendered QA, compare its built SHA with the latest independently approved descendant and inspect open defect gates. A successful URL for an ancestor already rejected for a surviving defect is historical diagnostic evidence, not the current candidate; hold existing QA children behind one targeted exact-head preview replacement, annotate their old handoffs as stale, and verify the replacement URL and SHA before they run. This avoids spending a full locale/accessibility matrix on a known-failing build or mistaking an attractive static preview for release approval.
- Match publication evidence to the task contract before releasing review. For `local-only`, a committed exact SHA in the shared local repository is reviewable from an isolated worktree or verified bundle; check `git cat-file -t <sha>`, ancestry, and a clean checkout, and do not introduce an unrequested push. For a PR/publication contract, push the authorized branch and verify the exact SHA resolves on origin before releasing the remote review.
- For ownership or de-duplication contracts, review the complete mounted surface graph—not only the named route file. Search app shells, global drawers, dialogs, mobile/desktop variants, and persistent overlays for the same API calls and lifecycle actions, then add a rendered regression proving those globally mounted surfaces cannot reintroduce the duplicate owner; route-source checks alone miss controls that remain reachable everywhere.

## Keep the review graph singular

- When a review handoff tool rejects the return because the review was dispatched directly in `running` instead of claimed from the review column, do not retry the rejected call: create one coder rework card carrying the findings verbatim (project-linked worktree, no parents so it dispatches immediately), link it as parent of the review, leave a pointer comment on the review, and unblock the review into dependency-wait so it auto-releases for re-verification. Downstream integration gates stay intact because they already wait on the review.
- If a pre-created review child exists, complete the implementation card to release it; do not also request same-card review.
- Before creating a task with forced skills, verify each skill is enabled for the assignee profile with `hermes -p <profile> skills list`. A skill available to the coordinator may be absent from a restricted specialist profile; never dispatch an unverified skill name.
- When a worker handoff says it created a review or fix child, inspect that child immediately before treating the gate as valid. Require a resolved project/workspace path, the intended parent, the exact final SHA, valid assignee skills, and a link to every downstream integration gate; replace an unresolved child before it burns two spawn attempts.
- On the first fast `pid not alive` reviewer failure, read `~/.hermes/kanban/logs/<task-id>.log` before retrying. If it reports `Unknown skill(s)`, either install or enable the intended class-level skill for the assignee profile and verify it with `hermes -p <profile> skills list`, or drop the forced-skill ref and re-dispatch when the card needs no specialist context from that skill; then separately harden worker startup so an unknown Kanban-only forced skill warns and continues while ordinary interactive CLI typos remain fail-loud. If the log reports an unresolved workspace, create one project-pinned replacement. Never spend crash-retry budget on an identical deterministic preflight failure.
- After two genuine reviewer runtime crashes, create one project-linked replacement review and link it directly to every downstream integration gate. Close the failed card as superseded only after the replacement records a real verdict.
- Keep a replacement independently runnable. Never add the failed card as its parent merely to satisfy a completion judge: that creates a dependency deadlock because the evidence needed to close the failed card cannot run. If administrative closure is rejected, leave the failed card open, run a sibling replacement from the last valid implementation parent, then close stale gates using the replacement's concrete verdict.
- If a provider safety filter blocks a defensive review before any verdict, preserve the gate and reroute it as local synthetic-fixture correctness testing to another suitable review profile. Do not reinterpret the filter refusal as code approval. Do not assume a higher model tier bypasses the same provider policy; change the task framing/profile and keep the review local, bounded, and evidence-based.
- Escalate model tier for reasoning complexity, not as a workaround for provider filtering or bounded markup/test fixes. A higher tier under the same provider can hit the same policy, while a focused UI correction with explicit failing assertions should stay on the normal coding tier unless repeated implementation failure or cross-system ambiguity proves it genuinely hard.
- After the second correction misses named acceptance criteria, compare the delivered result against the full contract immediately and escalate without waiting for a user status prompt. Stop the lower-tier lane before starting a replacement when both touch the same files; model switches require a new task, never a mid-session change.
- Treat reviewer-created corrective children as durable findings, not optional decomposition. Before closing one as duplicate, compare its named defect to the exact descendant diff; an approval that never exercised or changed the implicated code cannot supersede that fix.
- Never clear a gate administratively without equivalent evidence. A replacement review may supersede an old card only when it inspected the same final commit and criteria. If the old card names a superseded SHA, review both SHAs or rerun that gate with an explicit final-SHA correction.
- Normalize status by `(underlying defect, reviewed SHA, current descendant)` before reporting. Multiple reviewers reproducing the same assertions count as corroboration, not additional defects; a late result against an ancestor is historical evidence unless the finding is shown to survive in the current descendant.

## Bound release closure

- When the operator explicitly waives further review and orders deployment, stop the open-ended review lane before launching the bounded deploy; otherwise late reviewer children keep extending a release the user already chose to ship.
- Do not call a fix “final,” “finished,” or safe to resume downstream orchestration while any active reviewer or corrective child can still create a new release gate. Check the graph once, retain only the authorized install plus exact smoke tests, and report completion after that bounded lane closes.
- Before starting the next milestone phase, perform a graph-closure sweep across the completed implementation, every review child, correction child, administrative reconciliation card, and pre-created gate. Require each to be terminal with a verdict against the current descendant, or explicitly superseded by equivalent evidence. A late broad review of an ancestor can expose a defect inherited by the new phase; if it does, stop treating the descendant as approved, reproduce the finding there, and apply the correction on the newest descendant so already-completed work is preserved.
- Distinguish focused approval from full-contract approval in handoffs and status. A review that validates a two-file correction may inherit previously accepted evidence, but it cannot close unexercised geometry, accessibility, or mounted-surface requirements when another broad gate remains open; report the exact scope and keep the broad gate authoritative until it closes.
- Keep infrastructure hardening separate from the user's blocked product delivery. Apply the immediate profile/configuration repair first, let the product lane resume, and route the systemic guard as one background core task rather than making the product wait through repeated hardening reviews.

## Pause and resume safely

- When repaired credentials leave a stale quota/auth error on an otherwise-ready task and the dispatcher keeps guarding respawns, do not edit the database directly. Use the supported lifecycle to park the card briefly and unblock it with an audit reason; unblock clears `last_failure_error` and the consecutive spawn-failure count. Read the card back to confirm the marker is null and it is ready, dry-run dispatch to confirm that exact task is selected, then dispatch one task and read back a `running` status plus current run ID. A cleared marker or ready state alone is not proof that execution resumed.
- Treat a temporary pause as a graph mutation: block running and ready cards once, then inspect whether recurrence escalation moved cards to triage or triggered auto-decomposition.
- Block invalid decomposition children with no workspace before they consume worker slots. On resume, create one authoritative project-linked replacement instead of repeatedly unblocking unresolved children.
- When rebuilding a whole dependency graph as replacements, wire parent→child links and distinct per-task worktrees at creation and verify them on readback before the dispatcher ticks. Unlinked cards land `ready` and dispatch immediately and out of order — a baseline and its downstream review can be co-claimed into the same checkout — and a shared repo-root checkout across lanes is a provisioning failure, not a shortcut.
- Verify the Git base inside every first-wave worktree before releasing the graph: record `HEAD`, the approved base SHA, and `git merge-base --is-ancestor <approved-sha> HEAD`. Project linkage chooses where to create a worktree but may still branch from an outdated default ref; correct a fresh clean worktree before dispatch, and never reset a workspace that already contains product edits.
- When a run goes stale, preserve its commit and workspace. If the workspace contains uncommitted WIP, resume it with exactly one `workspace_kind=dir` task pointed at that existing absolute worktree path; a new project worktree starts from Git and cannot inherit uncommitted edits. Read the checkpoint and `git status` before changing anything, and pre-create the project-linked exact-SHA review separately.
- Enforce one writer per workspace. After the preserved-workspace continuation is claimed, immediately block or stop every older task that can spawn against the same directory; dependency links alone do not terminate an already-running duplicate, so two workers can otherwise edit the same files concurrently.
- On a `worktree target is checked out on another branch` preflight block, inventory every checkout of that path before touching anything: record each worktree's branch and HEAD and whether it holds unique uncommitted work or unpushed commits. Remove only a checkout proven clean and redundant (`git worktree remove --force` plus `worktree prune`), never one holding product edits, then unblock and confirm the dispatcher re-provisions. A stale implementation checkout next to a rework checkout is residue, not a second lane.
- When auto-decomposition has inserted invalid children into the canonical task's parent graph, blocking the children is not enough: they continue to gate the original card and may later spawn. Inspect every generated child before it runs. If its worktree path is unresolved, retire the malformed graph in dependency order (leaf children, aggregation/remediation cards, original stale card) and preserve the complete contract on one valid continuation plus one valid review. Cite the replacement's exact SHA once available. If a goal judge rejects administrative supersession because its contract names an older SHA, do not force completion; keep the stale card dependency-blocked behind the authoritative continuation, then close it using the continuation's verified exact SHA and review verdict.

## Isolate final certification

- Run final exact-SHA certification in a fresh project-linked worktree, not the implementation workspace. A reviewer running browser tests can create reports, screenshots, or `.last-run` files and make an otherwise clean candidate look dirty; judge candidate hygiene from the fresh checkout and separately verify that generated output remains untracked.
- Make test-server ownership explicit before browser certification: inventory required ports, terminate only verified stale owners or allocate isolated ports, start each required server under the test harness, and verify readiness before launching assertions. A suite that exits before tests because a port is occupied or a preview server is absent is **not** a product failure and is **not** a pass; rerun it in isolation and report it as unexecuted until assertions actually run.
- When a certification attempt contaminates only its own workspace with generated artifacts, do not mutate or recommit the candidate merely to delete them. Discard the reviewer worktree, recreate a clean exact-SHA worktree, and rerun the gate; this preserves the reviewed SHA and avoids turning harness residue into a source change.
- Before releasing downstream review, require all three identities to agree: local `HEAD`, remote branch SHA, and the SHA tested in the fresh certification workspace. A green run against an uncommitted tree or a different branch tip is evidence for debugging, not release approval.
