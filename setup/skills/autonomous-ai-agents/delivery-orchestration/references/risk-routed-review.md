# Risk-routed review and dependency hygiene

Apply this when creating or reassessing a delivery task. Reduce avoidable waiting, not the quality of consequential review.

1. **Preflight before dispatch:** Identify the acceptance criteria, smallest testable change, project branch/worktree, actual assignee and forced-skill availability, existing equivalent cards, and necessary dependency edges. Do not duplicate same-card review with a pre-created review child. Keep implementation ownership and one terminal review/release gate clear.
2. **Route by consequence and reversibility:** Small reversible copy/UI-only changes without auth, privacy, payments, data semantics, customer or release effects may finish with focused automated checks, implementer self-review, and real-running-UI inspection where relevant, but only if task and repository rules permit. Material behavioral changes receive one independent functional review. Auth, privacy, payments, migrations and production releases retain security/release specialists, exact-head CI and explicit human approvals as applicable. Never weaken existing branch protection to save review time.
3. **Parallelize only independent lanes:** Let functional and security reviewers inspect the same immutable candidate concurrently when needed, and join at the existing release gate. Continue on non-conflicting work while a review waits. Do not add serial review cards with overlapping scope or concurrent writes to the same file.
4. **Make one actionable handoff:** Supply exact commit/diff, requirements, observed checks and risks. Reviewer groups reproducible blocking findings by outcome and routes ordinary defects back to the implementer on the same card. Defer pre-existing issues separately and do not block on preference-only nits. A re-review checks the correction and affected regressions; reuse still-valid evidence rather than replaying an entire check matrix. If the same cause fails twice, repair the spec, task graph or approach instead of repeating a run.
5. **Diagnose review latency before raising capacity:** Read the live dispatcher concurrency limits, active workers, and reviewer/security cards by status and parent links; distinguish `todo` (parent-gated) from `ready` (runnable) and `running` (actual review). Check CPU load and available RAM against the host's capacity, then compare review-run duration with runnable-start delay and blocked time. Confirm actual admissions from run claims, PIDs, and worktree/project roots rather than treating on-disk generic per-profile settings as the loaded policy: a profile-specific exception or stale gateway can admit a different mix of workers, and two coder runs can occupy both global slots. Verify any project-isolation promise against *both* worktree roots before calling concurrent coders safe. Idle CPU does not imply spare Kanban slots, and a long parent-gated queue does not prove slow reviewers. For coder throughput, check the worker log for actual `delegate_task` duration and child terminal behavior before prescribing more subagents: one-shot Kanban CLI joins children inside the tool call, so a lone read-only child can lengthen the critical path instead of running beside the parent. If a delegated child receives the parent's Kanban completion nudge, fix the child-context gate with a regression test while preserving the real worker's end-of-task guard; do not count a child invocation as a speedup without measuring elapsed time. Before writing a capacity-change card, express the arithmetic explicitly as **existing slots + additional dedicated slots = total cap**, and name which profiles own each exclusive slot; a shared gate lane and one slot per gate profile are not interchangeable. If the owner corrects that scope, reconcile the card's canonical title/body and downstream activation contract *before dispatch* and read them back; a later superseding comment alongside contradictory numbers can leave a worker implementing the obsolete design. Treat an idle RAM snapshot as a screening signal, not proof that concurrent test/build peaks fit; require a guarded admission and rollback plan before activation. Compare task creation-to-verified-outcome lead time, review rounds and escaped defects for similar risk classes; include review children and release gates in end-to-end timing. Keep already-open dependency graphs intact unless their card is being handled; never cosmetically complete a gate.
6. **Recover productive worker loops:** After two clean-exit protocol violations or equivalent retries, inspect the live claim, heartbeat, exact worktree diff, commit and test evidence before another dispatch. If a worker is still active, do not reset, stash, or edit its checkout under it; leave one actionable board comment and let its current run settle. If it exits with sound work but no terminal transition, preserve that work and change the recovery route rather than repeating the same spawn. Separate provider errors from task-content failures; finish only after a real terminal handoff and independently verified checks, never because the worker sent heartbeats or produced a large diff.
