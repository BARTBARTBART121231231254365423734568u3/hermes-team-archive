# Hippe Flessen decisions
- Thomas chose **Klei & crème** among four related visual directions. Keep the storefront simple, products clear and ordering easy.
- Build an independent Railway-hosted webshop, **not Shopify**, with a mother-facing product/order dashboard and eventual shipping-label workflow. Do not treat Railway hosting as authorization for public deployment.
- Use clearly identified sample product images, prices and descriptions until real content arrives; keep these replaceable and demo products non-purchasable. For a WordPress-like back office, retain the independent app: let the sole mother-admin manage products/photos, categories, existing page text, coupons, sale prices and demo order workflows. Archive/restore products rather than hard-delete; never turn simulated orders into real paid orders.
- Distinguish commerce readiness from enabled commerce: make administration and server-side price previews work with persistent staging storage, but do not consume a coupon on preview or activate real checkout, payments, refunds, labels or shipping before providers, business inputs and release approval exist.
- The planning handoff must explain *how* implementation proceeds in detail: schema, API, files, interactions, tests and stop gates—not merely state desired outcomes.
- When Thomas says **Spark**, he means **Spark 1.3 Contributor** (`muse-code/muse-spark-1.3-contributor`); **Extra High** refers to reasoning effort (`xhigh`), not the model name. Pin implementation cards explicitly and verify run routing; a profile default or deterministic complexity routing can otherwise use a different model. For large multi-part builds, set `goal_mode` with a bounded turn budget so the builder works through to verified delivery instead of stopping after one shot.
- Require independent review and security go/no-go before claiming production or public staging readiness. Demo admin without vetted MFA/identity and persistence remains local-only.
- Staging admin credentials live only in Railway env vars — never in cards, repos, or proactive chat messages. Give them to Thomas only when he explicitly asks (login URL + email + password), and offer rotation.
- Thomas chose logo **02 Duo (B)** as the official mark; integrate that exact asset everywhere and do not invent a provisional mark.
- Keep exactly one order status filter (counters as calm text plus a single status select with search/sort/reset); remove any duplicate status-button row on both the admin overview and the full orders page.
- Finish the homepage 'Van klei tot fles' as a balanced Klei & crème process closure with truthful demo copy and no invented provenance or delivery claims.
- Review on a normal clickable full-site URL, not repeated loose files or a static-only replacement. Use a **real Railway `staging` environment** in the authorized project; a production environment with `staging` in the service name does not meet the request. Verify project/environment/service IDs, source branch and exact commit before deploy. Base `staging` on the newest approved commit chain — never push an older `main` over newer worktree/branch work. Never narrow an approved full-site scope down to a static-only/preview-only substitute to satisfy security or deploy pressure without explicit user authorization; stop the obsolete lane instead of repurposing it.
- Build readiness and public security are separate gates: make the Node app build and bind to Railway's `PORT` without weakening local fail-closed guards, but do not publish its former password/session/file-store admin just because startup and tests pass. Keep the full interactive storefront and protected working management with persistent staging storage; get independent functional and security GO on the exact candidate SHA. Demo checkout, payment and shipping remain disabled until separately authorized. Only devops deploys with a verified target manifest, and checks both permitted and denied live admin paths. A conditional code GO must list its unproven live points explicitly, and a prior NO-GO stands until each point has live proof. Close a superseded review as historical code-quality only and state explicitly that it authorizes no deployment. Verify the guard tooling itself first — never assume a `deploy-verified` command exists; if it does not, enforce the procedural equivalent (reviewed manifest checked against live status, then redeploy, then real HTTP checks).
- Before replacing a project or repository, distinguish existing resources from intended new ones. Preserve the last approved source locally, stop obsolete deployment lanes, and never reuse an old target implicitly. If deletion is policy-denied, leave that destructive action to Thomas and do not simulate it through another API/agent; resume creation under the same name only after verifying the old resource is gone.
- Seed a fresh empty GitHub repo from the exact approved SHA, never from a stale main: confirm emptiness first (`gh repo view` plus `git ls-remote` for HEAD and `--heads` returns nothing), confirm the SHA locally with ancestry (`git cat-file -t` plus `merge-base --is-ancestor`), push the same SHA to both `main` and `staging` through a temporary remote, verify via `ls-remote`, then remove the temporary remote so the old `origin` is never overwritten by accident.
- For Railway, create an Empty Project with the required name first, then link the new GitHub repo inside it (New -> GitHub Repo) with source branch `staging`, plus a real `staging` environment and private database — a production environment carrying `staging` in a service name does not satisfy a staging request. After wiring, read back live state before claiming anything: link project+environment, confirm the service source branch, confirm the database service exists, set staging vars without redeploying each time, generate the public domain, then check service status/replicas and tail logs — a crash with a fail-closed boot message means a config gate is working, not a successful deploy.
- Keep staging fully Railway-native: it must boot with only Railway env vars, the private Postgres reference, and env-admin credentials — never hard-require an external identity provider or other external runtime for boot. An external IdP/domain/billing change is a design proposal, not authorization; if one is ever proposed, keep it optional behind explicit approval and keep the Railway-only path working. The user reads any external boot dependency as partial hosting elsewhere, and a missing external config then crash-loops the deployment.
- Railway's private Postgres presents a self-signed internal certificate, so a minimal pg client with strict TLS verify crash-loops with a certificate-chain error — accept an explicit no-verify mode scoped to the internal host only, and keep strict verification everywhere else.
- When a vetted dependency cannot be installed in the worker environment, do not silently substitute it — implement the closest equivalent, record the exact deviation with its replacement path and test equivalence, and flag it explicitly for reviewer/security.
- When creating a project-linked code card (`project` + `workspace_kind: worktree`), omit `workspace_path` so the dispatcher assigns the canonical `.worktrees/<task-id>` — a custom path fails preflight as not task-owned. On a preflight block, create a corrected v2 card instead of unblocking, mark v1 superseded by comment, rebuild the dependent review/security/deploy chain behind v2, and leave an already-gated v1 sibling blocked when it wakes the same way.
- When two reviewed SHAs share one base and must ship together, merge or cherry-pick both onto `staging` and push the merge result — never force through conflicts, route those back to coder. Then redeploy and verify live.
- When Thomas asks whether the site is online, answer from a fresh live readback (service status/replicas plus HTTP spot-checks of homepage and the newest route), never from board state or a healthy-looking deployment record alone — say plainly that it is not live yet when the new deployment is still building.
- When a deploy gate waits on authenticated live proof, verify it yourself with read-only checks: GET the login page, POST the credentials with that page's fresh single-use CSRF token in one quick flow, then load each admin page and API as that session and confirm anonymous calls are denied — record outcomes on the card without credentials and unblock. Retry a rejected login form as one fresh flow first, because a token issued just before a deploy can belong to a draining instance and fail; never persist test mutations to staging, the integration suite owns the write paths.
- When a planner spec lists open user questions with proposed defaults, build with the defaults and surface the questions once at delivery — do not stall the lane or ping Thomas mid-build.

## Translating storefront feedback into an implementation brief
1. Inspect the current rendered pages, source templates, design decisions, and active branches/worktrees before naming UI elements or paths; a main checkout may trail an active preview branch. Separate what is already implemented from what the user wants changed.
2. Preserve the existing Klei & crème tokens, typography, and demo-only safeguards in both server-rendered pages and generated static preview. Write acceptance criteria for desktop/mobile interaction, keyboard access, filtering state, and actual verification rather than prescribing cosmetic CSS alone.
3. When status tabs duplicate an existing status selector, remove the redundant tabs and keep the selector, search, sort, reset, and counters working together. Do not add a filter the user has explicitly withdrawn.
4. For collection facets, expose the requested individual expandable controls directly (color, material, volume) instead of hiding all three behind a general Filters control. Preserve combined query parameters, search/sort state, reset, and static-preview links; test each facet and cross-facet round trips.
5. Treat explicit permission to add a logo as permission to include it in the current implementation, not a reason to defer. Find the real project asset first; if none is supplied, use a brand-consistent provisional wordmark clearly identified as provisional, never invent an approved official logo.
6. When requested to make a master prompt rather than implement, deliver a ready-to-paste imperative brief with scope, house style, boundaries, acceptance criteria, and verification; do not create implementation cards or modify the app unless separately asked. If asked to question the user first, resolve only consequential ambiguities (especially order handling and whether 'working' includes real payment/shipping), then encode the answers as fixed decisions so the coding agent need not rediscover them.
7. When Thomas sends screenshots with numbered change requests, inspect every image with vision analysis before writing the brief, and turn each numbered point into its own acceptance criterion — never translate numbered feedback from the text alone, since the numbers refer to visuals the text does not describe.
