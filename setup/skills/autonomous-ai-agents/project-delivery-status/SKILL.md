# Project Delivery Status

Coordinate and report multi-agent product delivery so Thomas never has to discover stalls, repeated misses, or scope drift himself.

## Procedure

1. **Keep one originating conversation for each delivery.** Identify the requested scope first: product delivery stays project-pure, while a whole-agent or infrastructure program gets one system-wide channel. Record the originating session as the sole subscription destination for program and child-card notifications while chat updates are wanted. If Thomas opts out of a chat's updates, change or remove that chat's notification subscriptions across the active program and child cards, then read back each affected target; merely withholding assistant replies does not suppress automatic Kanban notifications. Preserve board/desktop visibility and any approved alternative destination rather than redirecting to a guessed chat. Before subscribing a child or reporting across sessions, inspect existing `hermes kanban notify-list <task_id>` subscriptions and the current `HERMES_SESSION_ID`; remove duplicate subscriptions from other sessions only after confirming the intended destination remains subscribed, then read back the target subscriptions. Duplicate session subscriptions cause parallel, conflicting-looking updates even when the board has only one workstream. For an exact-origin outbound receipt gate, create a finite read-only completion probe from that originating conversation, verify its subscription target, and require its completion notification to appear in that same conversation; a completed card or subscribed flag alone proves no delivery. Report only directly causal cross-project blockers.
2. **Read live state before every update.** Inspect the active implementation, review, and deployment cards, including their newest event and comment. If the original implementation has been reassigned, decomposed or moved back to `todo`, follow its current prerequisite leaves instead of repeating the last worker update. When the last implementation leaf completes, inspect the aggregation root and its existing review/release children immediately: leaf completion may only requeue the root, not start Security. Check root ownership before doing coordinator acceptance work and again before a lifecycle transition; if another worker has claimed it, send that worker any new exact-SHA evidence rather than duplicating the audit or completing its active run. Inspect leaf priority and dispatch evidence after every decomposition and review verdict: both auto-created children and reviewer-created repair cards can silently default to priority zero while the original delivery retains high priority. Read back each new critical-path card immediately and preserve the original delivery priority, verified workspace/test interpreter, required routing override and existing review/release dependencies. Repair missing scheduling metadata on the existing unclaimed card instead of creating another replacement. Distinguish 'priority restored; still queued' from a verified new run. Before saying work resumed, inspect both the global worker limit and the assignee's active claim, plus current dispatch guards. Priority selects the next eligible task; it does not preempt an occupied worker slot. If capacity is the blocker, say which active role/work holds it and that the task is still queued in the same update, rather than making Thomas ask why it has not started. Do not raise concurrency limits or interrupt unrelated active work merely to make a resumption claim true. Attribute worker-reported test counts to their tested phase; do not imply partial tests prove the unfinished integration. Report `running` only with a current run and recent heartbeat. For a concurrency claim, compare board claim/completion timestamps, distinct run IDs/PIDs/sessions and repository worktrees; require an overlap interval and prove the next queued worker was claimed only after capacity freed, rather than inferring parallelism from two completed cards. For a rollback-to-one-worker claim, test two disposable cards against the **running gateway**: hold the first slot and require the second claim to occur only after the first completion. Verify both `claimed.lock` values identify the gateway's current PID, as a separate CLI dispatcher can produce correct ordering without proving gateway enforcement. A configuration-file or CLI readback proves disk state, not a live dispatch limit; inspect whether settings are loaded at process startup and require a drained restart when they are. If both cards claim together, stop new admission probes, preserve event evidence, and keep acceptance gated until a boot-loaded one-worker limit passes. Restore the intended two-worker policy only through a separately guarded, drained restart and re-prove live admission. For Thomas's required SSH restart, send the exact command and confirmation phrase only after the backup, procedure dry run, and worker drain are verified; distinguish a dry run from a restart and do not ask him to act early. Distinguish execution from lifecycle lag: a fresh commit/test comment proves work was produced, but if the worker has not requested review or completed the card, say "the fix is committed and tested; handoff is still pending" rather than claiming it is still working. Call `ready` queued, never active. If a ready card repeatedly fails to dispatch, inspect its newest dispatcher events and failure fields for stale retry/auth guards; distinguish this queue blocker from the product's implementation state, and route an authorized recovery rather than describing it as active work.
3. **Build team-wide status from two layers.** Start with one unfiltered `kanban_list(include_archived=false)` snapshot, then call `kanban_show` only for `running`, `review`, and `ready` cards to recover current evidence, requested changes, and remaining gates. Refresh the machine-generated team report when the installation provides one, but treat it as a summary rather than authority: cross-check its timestamp, service health, and card claims against direct probes before reporting them. For multi-stage programs, cross-check the completion handoff against its original acceptance scope; label an audit or backup as such, not as applied remediation, even when the stage card is done.
4. **Separate delivery work from backlog inventory.** Lead with what is executing, what is queued for review, what is safely gated, and recent verified throughput. Put aggregate `todo`/`blocked` counts last and qualify whether they are active incidents or accumulated backlog; raw counts without classification create false urgency.
5. **Use live chat requests as transport evidence carefully.** When a status request arrives through a channel being repaired, record it as successful inbound delivery and produce the response from live Kanban state. If successful inbound delivery directly satisfies a stale human-input or pairing blocker, clear only that prerequisite and return the verification card to `ready` so the team resumes without asking Thomas to manage it. Keep outbound delivery/readback, restart survival, authorization, and end-to-end acceptance as separate gates; receiving a message proves none of them.
6. **Own release-blocking stalls without transferring coordination to Thomas.** Diagnose blocker, stale-guard, quota/auth and dispatch failures as soon as discovered, then act through the existing delivery graph. For Thomas, Mr. in Control is the default coordinating owner and Discord is a decision-only channel: keep internally solvable stalls, recovery attempts and resumptions on the board, not in unsolicited chat alerts. Interrupt him only for a critical decision or concrete action the team cannot provide; use the verified approval interface for that proposal. A direct status question permits one concise answer, not a stream of repair narration. For users who explicitly request operational alerts, report the blocked gate and recovery in their chosen origin channel. Before authorizing an unattended or overnight run, probe provider quota and auth health first and name it as the top risk in the authorization summary — a walled profile stalls every gated lane at once, and an overnight run authorized without that check oversells what the board can deliver. Name the blocked gate, impact on the overall flow, what recovery is underway, and whether Thomas must act. When approval is the missing prerequisite, inspect the latest task run, originating project session, binding contract, and prior owner answers; assemble ONE complete proposal covering all still-open material decisions before asking. Ask in that project's originating conversation or its independently verified decision channel, never in an adjacent project/infrastructure chat — cross-project prompts mix contexts and partial answers cause repeated block/unblock loops. Keep the dependent task gated until every required value is confirmed and read back; a blocked-card notification, partial approval, or apology does not authorize the remainder. If an unattended worker cannot execute an approved maintenance operation, route it to a capable interactive execution path rather than repeatedly unblocking the same incapable run. Do not wait for a status question to investigate or repair the stall. Send a resumption alert only when operational alerts are explicitly requested; otherwise record the transition internally and contact Thomas only if an irreducible human action remains. Distinguish routine queued work and non-critical backlog from a genuine critical-path stall. Do not imply background monitoring or promise a future alert while the session is inactive unless a verified watcher/notification mechanism is actually configured. Before telling Thomas he can leave for an errand or gym, check whether the remaining gate requires his SSH presence; either complete that operator action while he is available, arrange and verify an independently approved operator outside the gateway cgroup, or state plainly that the safe pause will wait until he returns. Do not give a short completion estimate that quietly assumes he can restart remotely.
7. **Consolidate meaningful updates in the origin session within its notification policy.** When updates are requested, send one short update for a meaningful gate change rather than narrating every commit, retry or child-card event. Thomas's Discord decision-only policy excludes routine approval-pass, activation and completion announcements as well as progress; preserve those results on the board/desktop instead of moving the noise to a different Discord channel. A Kanban status notification is a trigger to inspect the board, not a direct question or an invitation to echo the event back to the chat. When Thomas asks to be told when it is ready, treat that as one final verified-outcome notification in the originating conversation, not permission for every child-card completion recap. Persist that scope on the final release/acceptance card and verify the actual delivery subscription; a board comment alone does not schedule or prove a notification. When Thomas opts out of chat updates, treat the originating chat as assistance-only until he explicitly reverses that preference: first verify its automatic Kanban subscriptions are disabled or rerouted to an approved non-chat destination, then inspect any residual automatic notifications and act on existing board cards silently. Do not send an acknowledgment, a 'no help needed' reply, or a completion recap for each notification; even a one-line no-op response is another unwanted channel message. Send a chat message only if a decision or action that Thomas alone can provide is necessary, or when he directly asks a question. Keep all other diagnoses, gate changes, and handoffs on the board. Bound the acceptance matrix before scheduling probes: separate the required user outcome from optional resource/stress telemetry, reuse live evidence already obtained, and request one independent verdict once mandatory gates are met. If review finds a real gap, execute only the named finite check or report a specific deferral; do not extend a working delivery through successive broad test rounds. When Thomas asks why it is slow, own the excess verification plainly and state the one remaining gate. During authorized overnight work, keep routine transitions on the board for the morning summary; interrupt Thomas only for a decision the team cannot resolve. Preserve the product pause separately from permission to finish infrastructure work.
8. **Normalize repeated reports.** Group by underlying defect and reviewed SHA. Say one defect was independently reproduced twice; identify late ancestor-SHA reports as stale when the current descendant already fixes them.
8. **Audit every correction against the full contract immediately.** Compare the handoff and diff/test evidence with every named criterion before calling it complete. If criteria are missing, route correction before reporting success. For a completed operational phase, read its handoff and artifacts and separate inventory, backup/restore proof, applied remediation, and live verification. A read-only audit with deferred fixes does not complete an implementation phase merely because its card says done. Assign each required unresolved finding to an executable corrective owner and retain the downstream acceptance gate; obtain explicit scope deferral for anything intentionally omitted. Do not enable extra channels, widen permissions, or perform destructive cleanup just to clear an inventory finding—verify user intent and authorization first.
9. **Escalate repeated misses without prompting.** After the second materially incomplete correction against the same contract, stop conflicting lower-tier work and create one higher-capability replacement when complexity warrants it. Preserve the exact base SHA and all unmet criteria; never switch models mid-session. After a user-operated command fails, check for a *claimed, active* repair task immediately; a board comment or prior security approval is not a team member working on the new failure. If no repair is active or queued, create one narrowly scoped corrective card with a real-path regression test before saying the team is fixing it. Report `ready` as queued, not active, and give the user a fresh command only after exact-head review and a live dry run.
10. **Turn user cost limits into release gates.** When Thomas gives a free-tier, budget, quota, or “do not exceed” constraint, copy the exact numeric limits into both the implementation/deployment card and the final acceptance card. Require a conservative worst-case storage/operation estimate with headroom before activation; stop for a decision instead of enabling paid overage or unbounded retention/polling.
11. **Surface external-account prerequisites early.** Before promising an end-to-end cloud deployment, probe whether the assigned worker actually has the provider account/API credentials, secret injection, and resource-creation rights. If not, request the minimum operator action once, name only the secret-variable slots (never values), and do not claim Thomas has nothing to do.
12. **Keep credentials out of the coordination surface.** Open the provider or deployment UI for Thomas to authenticate or enter secret values directly; never transcribe credentials from chat or screenshots into commands, comments, reports, or cards. Verify only secret presence, scope, and a redacted connection result before resuming.
13. **Validate launch authority and every child workspace before dispatch.** When Thomas names a specific model and reasoning effort, resolve its exact provider/model ID from the local model catalog, pin both on every implementation and rework card (including reviewer-created corrections), set the per-model effort on the executing profile, read it back, and verify the run-linked routing event at claim; a task-body instruction alone cannot override deterministic routing. If a correction card lacks the required override, stop it before edits and replace or repair the route without duplicating work. For repository work, create project-linked children (or an explicit existing directory) and confirm a non-empty workspace path before relying on them. Check that the *creator profile* resolves the project, then read back each card's project ID, worktree kind, branch and path: a profile-local project registry can silently turn an unresolved project-linked request into scratch. Gate malformed cards before they claim; archive invalid replacements before their parent completes so they cannot re-admit. Compare required local inspection tools with the assigned profile's *launch-platform* toolsets, not its role name; a web-only researcher cannot perform local source or SQLite audits. Check the effective skill set for each lane, including review skills automatically injected by the dispatcher, against the actual assignee profile before claiming a run. When a reviewer startup fails on a missing forced skill, preserve the same card and independent review gate, provision/verify the required skill if authorized or route to a capable independent reviewer, and regression-test preclaim validation so retries cannot repeatedly crash. Do not let auto-decomposed no-workspace cards become release parents; replace or supersede them immediately because repeated spawn failures create noise and can deadlock the graph.
14. **Keep the release graph minimal and fail closed on a NO-GO.** Before linking a replacement, inspect the existing parents and children, then re-read the root immediately before creation and again before linking: another coordinator may provision the same repair between reads. Use a stable idempotency key for the outcome, not a locally unique label; if a concurrent equivalent appears, keep one executable lane, archive the unused cards before they claim, detach their release-parent edges, and verify the surviving graph. A reviewer card completed with a NO-GO still satisfies its Kanban dependency; before that completion releases integration, link the existing rework and a fresh exact-SHA approval gate as parents of the downstream card, then read back its parents and status. Pin the corrected SHA in independent functional/security checks when required, and make their combined approval—not completion of the rejected review—the release condition. Reuse existing review/rework cards first; close obsolete dependencies with concrete successor evidence rather than stacking duplicate reviewers that later block deployment.
15. **Report the product, not the process.** Once Thomas authorizes execution, keep tool calls, retries, hypotheses, and intermediate fixes internal. Send only the verified final outcome; interrupt him only for a blocker that requires his action or a decision that changes scope. For an explicit status request—especially after repeated gate-pass notifications or frustration—lead with the live verdict in plain Dutch (for example, `werkt nog niet`), then name the ONE effective blocker and whether anyone must act; omit approval history, cards and narrated retries unless he asks. Verify the installed revision and live interaction rather than inferring them from local code/package approvals. If a productive worker prevents a gateway restart, say that directly and do not promise automatic activation without a verified independent operator or trigger. When Thomas points out repeated failed attempts, stop presenting the same unexecutable path as fresh progress: verify whether a genuinely executable route exists, then either use it and report its readback or plainly say no action occurred and state the one remaining operator gate. Do not promise another restart/test from a session that cannot survive or perform it. If he asks whether "the test" worked in a multi-gate rollout, answer by tested phase: name the specific live probes that passed, the final acceptance probe that has not passed, and the *currently effective* runtime policy after any rollback. Do not let an earlier passing concurrency smoke test stand in for post-restore reproof; startup-loaded configuration can differ from both the disk readback and the policy under which that earlier test ran.
16. **Include the review target when a human visual gate remains.** Before sending the status, determine whether the exact candidate is live on staging, available through a verified external preview, or represented only by local evidence. State that distinction explicitly and include the verified clickable target in the same update when one exists. For a local HTML preview, check the exact candidate's source commit, serve its built directory over loopback, verify the target routes, then open and read the rendered preview pane; a 200 response or pane-open acknowledgment alone does not prove that the pane shows that candidate rather than a previous snapshot. Keep authenticated admin behind its local access boundary; a static shop snapshot does not demonstrate a working admin wizard. Never make Thomas ask a second question to discover how to review the release candidate, and never present a healthy staging URL as the candidate unless its deployed revision matches the gated SHA.
17. **Translate approval into the narrowest authorized gate transition in the same turn.** After an explicit go-ahead, use `kanban_comment` to persist the approved scope on the blocked executable card, perform the authorized gate transition with `kanban_unblock` when prerequisites permit, and read that exact card back with `kanban_show` before acknowledging that work can resume. For approval conditional on a scheduled backup or other future event, inspect the actual schedule and timezone, keep the release gated until the event's artifact is independently verified, and use a durable external operator/checkpoint rather than an idle gateway worker or a wall-clock-only restart. For backup gates, inspect the archive manifest for expected live databases/configuration, perform an isolated restore and database integrity/read check, and correlate its creation with the scheduled run; a cron `ok` can still describe an empty archive. Before claiming a future activation is arranged, read back the external timer/service and its guard state; if authorization or safety policy disarms execution, stop the no-op timer and report that an interactive operator is still required. A conversational acknowledgment or a queued card does not create a future execution mechanism. If the turn was interrupted, reconcile the latest approval against the card before answering the next status request; do not ask Thomas to repeat an approval that remains valid. Distinguish user authorization from any separate tool-level safety approval, and never bypass the latter. Record the exact candidate and evidence Thomas approved, then release only the next gate he authorized. If he asks to review staging before continuation, model staging, production, and the next milestone as separate cards/gates before dispatch: complete the staging card after live verification, keep production blocked for explicit approval, and keep a separate approval parent on the next milestone. Use `needs_input` at most once on a legacy combined card; repeated intentional blocks can trigger block-loop triage even though the requested checkpoint succeeded. Dependency readiness is not authorization to advance beyond the stated checkpoint.
18. **Label visual evidence by scope.** Say whether screenshots show the full page, a crop, an isolated component, or a synthetic state. Before answering that an established element was removed because it is absent from a crop, inspect the full route or implementation and distinguish “not shown in this evidence” from “not present in the product.”
19. **Use completion language strictly and name the scope.** `Done` means every gate in the *accepted scope* is evidenced. If Thomas explicitly accepts an operational subset while a stronger original acceptance gate remains unproven, record a separately completed operational milestone and label the original full-acceptance card unfulfilled; never complete its parent graph merely to turn it green. State the missing proof once, park further probes, and ask for no repeat operator commands unless he freshly authorizes that separate work. Do not say “final” or “fully released” while required original gates remain open.
20. **Define the denominator before giving a percentage.** For “how far are we?”, lead with whether the estimate covers the entire approved plan or one feature. Read the critical-path implementation, review, activation, and acceptance cards; distinguish completed planning from delivered functionality. Prefer “planning complete; implementation not yet verified” over an invented overall percentage. If a percentage is useful, label it approximate, explain the milestone weighting briefly, and compute it from evidenced milestones rather than equal card counts. State the headline feature's separate status in the same update so Thomas need not ask whether whole-program progress means that feature is working. Do not count task creation, reassignment, or recovery retries as implementation progress.
21. **Preserve compound approval gates literally.** When Thomas asks for a plan now and implementation only after another lane finishes and he accepts, block implementation immediately and record both conditions. Deliver the plan without executable implementation children becoming eligible. Completion of the other lane alone is not permission. When a later explicit go-ahead supersedes that dependency, record the revised authorization on the same coordinating card before unblocking; preserve any separately paused product work. For unattended execution, persist the scope and restart/activation permission on both the program root and the downstream release card so workers can proceed without re-asking; verify the only notification subscription is the originating session. Treat an offer to be reached on another channel as conditional: check the private destination and actual delivery first, never assume transport works because a channel is configured.
22. **Queue post-delivery add-ons without widening the active program.** When Thomas requests a third-party Desktop plugin after infrastructure delivery, inspect upstream source/install scripts and the Desktop SDK, and allow source/security review in parallel; gate installation on the exact reviewed revision and the infrastructure outcome he *actually accepted*. If he explicitly accepts partial operational delivery and separately authorizes the add-on despite an unproven full gate, do not falsely complete that gate or leave an impossible full-root dependency as the only execution route: create one narrowly scoped executable continuation behind the accepted operational milestone and exact-revision security approval, mark the old full-gated card superseded, and check both states to prevent duplicate installation. Treat code-only security approval as distinct from authorization to migrate existing unowned directories: inspect their ownership and contents, obtain a scoped disposition before replacement, and honor any backup waiver only for the named paths. Resolve the actual Desktop host separately from the gateway host—backend and UI may load on different machines. Before building a client package or promising autonomous installation, prove a write-capable path to the actual client and a way to inspect its rendered UI; window metadata and a gateway-local plugin file prove neither. If that path is absent, report the single concrete access blocker without handing Thomas a ZIP, manual hash check, or screenshot chore when he asked the team to do everything. Verify the rendered widget with real provider data or an honest provider error before declaring installation complete. Read the Desktop Plugins page as two independent halves: Desktop-column ON versus `—` and Agent-column ON versus `—` are separate states — Agent ON with Desktop `—` means backend-only with no visible widget, and `copying...` means the Desktop half is still installing, so never claim the UI is ready from Agent ON alone. Keep optional browser-cookie readers off unless separately requested. Keep the add-on outside the original program's release gate and preserve any separately paused product work.

## Pitfalls

- Never make Thomas discover whether work is active: verify and repair stalls internally, and surface only a decision he must make or an accurate answer to his explicit status request; automated blocker/done messages are not permission to add reassuring replies.
- Never merge unrelated work into a product-channel update; cross-project noise makes status untrustworthy.
- Never treat a provider refusal, crashed reviewer, administrative closure, or passing broad CI as approval of untested acceptance criteria.
- Never launch concurrent replacements that touch the same files; stop or gate the stale lane first.
- Never summarize only aggregate board counts as project status; filter to the originating project and inspect its active/queued gate cards, because a global snapshot mixes unrelated backlog with the actual release state.
- Never call a ready-but-guarded card merely queued without naming the dispatch guard when known; the distinction tells the user whether work is waiting normally or requires internal recovery.
- Never attach an administrative duplicate as a required release parent merely to satisfy lifecycle bookkeeping; use one executable project-linked continuation and preserve evidence in comments or completion metadata.
- Never convert a budget screenshot into a vague “stay cheap” note; preserve the stated storage and operation ceilings as measurable acceptance criteria because retention and health polling can create overage independently.
- Never repeat a monitoring report's outage claim when a direct configured-endpoint probe contradicts it; report the service truth and the monitoring mismatch separately because stale paths and timestamps can create false incidents.
- Never call a queued review active merely because a candidate exists; require a claimed review run or fresh reviewer heartbeat because `review` is a workflow state, not proof of execution.
- Never imply work progressed while the local host was off or asleep — the gateway, dispatcher, and workers all stop with it, so attribute quiet gaps to that and prove resume with fresh heartbeats.
- When Thomas says an agent does not look active, reconcile the visible status with the latest heartbeat, commit/test evidence, and terminal lifecycle event. State the exact discrepancy and next gate; do not defend the status label when the work has finished but the card has not transitioned.
- Never declare a messaging repair end-to-end from inbound evidence alone; confirm outbound delivery or readback separately because the two directions can fail independently.
- Never describe a user-supplied image from code or log inference: if the vision tool returns no usable image, say so immediately instead of reconstructing what the screenshot supposedly shows, then verify the underlying state another way.
- Before estimating time to completion, separate queue wait, remaining implementation, review and activation. Inspect current claims, effective capacity, dispatch guards and comparable completed-phase durations. Failed or materially incomplete attempts are not throughput evidence; multiplying an assumed duration by the number of cards produces only a planning scenario, not a reliable ETA. State whether a range starts now or after pickup, and label unknown pickup time explicitly. If no defensible finish time exists, say so once and identify the immediate constraint rather than renewing a speculative countdown after each status question.
- Report a changes_requested round as a normal rework cycle — finding count, scope, and next holder — never as a failure; a review gate catching contract gaps is the process working, and framing it as bad news trains the user to dread the gate that protects them.
- Treat parked work as parked until Thomas explicitly unparks it; a milestone finishing does not unpark it. Keep the artifact pointer and resume preconditions recorded, and take no runtime, capacity, restart, or board-mutating action on the parked effort meanwhile.
- When a review run cannot return findings to the implementer through the review tool (e.g. it rejects the handoff because the run was dispatched directly rather than claimed from review), carry the findings in a linked implementer rework card and re-gate the review behind it — do not leave the review blocked or ask the reviewer to retry the rejected call, because the dispatch mode that caused the rejection will not change on retry.
- Never accept a worker's 'file not found' before re-probing the exact quoted absolute path yourself — searches and unquoted globs silently miss repository paths containing spaces, and a recovery comment with the verified path plus the file attached to the card unblocks the worker without Thomas.
- Write project-link and workspace-kind requirements into the planner decomposition brief itself — post-creation validation catches undispatchable cards, but a brief that does not mandate project-linked worktree cards and forbid unverified forced skills reproduces the same provisioning failure on every program it decomposes.
- Attach on-disk evidence to a card with the file-path attach command instead of round-tripping file bytes through the session — it keeps large artifacts out of the context and lands them as durable task attachments.
- Answer status replies in the language Thomas is currently using — a Dutch question gets a Dutch answer — while cards, evidence, and prompts stay in the board's working language.
- For a stop-at-checkpoint request, park every ready lane immediately, let the running lane land, then park each child its completion releases before the dispatcher claims it; report the frozen resume state (candidate SHAs, queued lanes, unpark order) rather than letting the graph advance one more step.
- Never present a policy/identity file edit (SOUL, config text) as the behavior itself — it declares intent only; implementation, independent review, and live transport verification remain as separate gates.
- When the gate requires exact-head review or a published preview, verify the candidate SHA exists on origin at every implementation handoff: run `git ls-remote origin <task-branch>` and push the branch yourself if the worker left it local-only — reviewers and preview builders verify immutable remote SHAs, and an unpushed commit stalls both while reading as missing evidence.
