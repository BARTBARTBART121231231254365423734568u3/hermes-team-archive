# Kanban Runtime Graph Recovery

Recover delegated delivery without losing uncommitted work, duplicating edits, or trapping valid work behind malformed cards. See `references/manager-gate-context-recovery.md` when a manager-only gate refuses an inherited delegated-child context.

## Procedure

1. **Identify the authoritative state.** Inspect the root task, every child, the exact candidate SHA, and any workspace containing uncommitted changes. Compare stored task bodies and attachments with the original source before dispatch or resume; a literal truncation marker or incomplete exact-value list invalidates the contract even when card creation succeeded. Recover the full source first, then read back the repair instead of unblocking the same clipped input. Separate real implementation evidence from administrative or spawn-failure cards. Immediately before creating replacements, re-read the live parent/child graph and ready/running cards **without relying solely on a tenant-filtered list**: a concurrent coordinator's replacement may have a null tenant while still targeting the same repo and SHA. Compare workspaces, target files, and descendants, then re-check once more before linking so concurrent repairs do not create two executable owners.
2. **Choose one implementation owner.** For committed work, create a project-linked `worktree` task from the exact SHA. For preserved uncommitted work, create one `dir` task using the exact absolute existing worktree path.
3. **Stop collisions before dispatch.** Block or stop the former owner before the continuation is claimable. Never permit two workers to edit the same directory, even when one is described as a reviewer.
4. **Build a minimal graph.** Use one executable implementation followed by one independent review. Resolve the project repository and exact base first; for every project-linked worktree card, omit `workspace_path` at creation so the dispatcher assigns the task-owned canonical `<repo>/.worktrees/<task-id>` path. Do this independently for implementation and review, and read back both paths, project IDs, assignees and dependency links before either becomes claimable. Link the review only to the executable implementation. When repeated implementation attempts stop on environment setup, give DevOps one bounded prerequisite with a verified-environment handoff rather than repeatedly restarting the coder. Link that prerequisite as a parent of the existing implementation, preserve its worktree and downstream review, and unblock into dependency-gated waiting. This makes verified prerequisite completion resume the same owner without duplicate implementation lanes. Keep internal repair on the board; escalate to Thomas only for a specific permission or action the team genuinely cannot provide.
5. **Handle malformed cards honestly.** Keep cards with unresolved workspaces blocked or mark them superseded only after a real replacement produces the required evidence. Never fabricate a SHA, test result, or completion summary to satisfy a goal judge.
6. **Verify live routing and scheduling inheritance.** When reusing an existing review child after a correction, add the correction's exact immutable SHA and ancestry to its handoff before dispatch; its original body may still name the rejected candidate. Inspect `git worktree list --porcelain`, the review checkout's `git status --short --branch`/HEAD, and its expected branch ref as soon as the corrected parent completes: automatic dependency promotion can make the reviewer claimable immediately. If a clean isolated checkout is still on the rejected SHA and its expected branch is unused but stale, archive that ref, switch the checkout to the verified new commit, create the expected branch there, and verify clean status plus ancestry before reviewer dispatch; never reset or discard unique or uncommitted work. This administrative alignment is not independent review or approval. After creation, linking, retry or automatic decomposition, read the root and every executable leaf back. Compare each leaf's priority, assignee, workspace, approved base, model/provider overrides and unmet parents with the original delivery contract; valid paths alone do not prove schedulability. When automatic decomposition publishes a preview of an obsolete or rejected SHA, do not let ready QA children treat its URL as current evidence: gate the existing children behind one exact-head preview build, annotate their handoffs with the immutable SHA and static-preview limitations, and verify the resulting parent links before dispatch. A completed NO-GO QA child releases its parent dependency mechanically but does not grant acceptance; record the failed verdict on the parent and keep human acceptance and deployment closed until correction plus changed-head review. Restore accidentally lost priority on the existing unclaimed cards rather than creating duplicates. Serialize cards sharing a dirty worktree before admission, preserve the verified test-interpreter handoff on each leaf, and retain the original review/release gates. Use native board operations where available; for a missing edit operation, inspect the installed supported API before making a narrowly scoped, audited change and read back the exact targets. If a guarded update affects zero rows, re-read the task before retrying: another coordinator may already have repaired it, so a second unconditional write can overwrite a valid workspace or active run. Check queued routing intent separately from the next run-linked routing event: `ready` proves eligibility, not execution, and an override proves configuration, not the model actually spawned. When the user mandates per-lane model routing, record the mandate in the orchestration brief and verify each lane's run-linked routing event names the mandated model — never guess an unavailable model identifier, and block honestly rather than silently falling back to another model. A standing routing mandate does not inherit to auto-created children: rework, preview, and decomposed cards arrive without pins or project links, so re-verify and re-pin each before it dispatches rather than reclaiming after it starts on the wrong model.
7. **Consolidate user updates.** Report the one authoritative task, exact SHA/base, real passing gates, remaining blockers, and whether production was touched. Treat malformed-card notifications as administrative noise unless they changed the dependency graph.

## Dependency rules

- Never make a malformed or incomplete card a parent of its valid replacement. Parent links are gates, so this strands the replacement behind the card it must supersede. When a valid `todo` card refuses to promote, inspect the exact unmet parents before editing: parked auto-decomposed duplicates can deadlock it, but genuine prerequisites must remain. Detach only verified obsolete edges through the supported board surface described below, then read back readiness; do not use a forbidden shell CLI as a shortcut.
- Never attach a speculative auto-decomposition subtree to an authoritative root that already owns uncommitted work. Auto-created children can reassign or resume the root and cause same-worktree collisions.
- If goal mode decomposes into no-workspace children, stop the root before it resumes, preserve its workspace, and rebuild the lane manually with explicit project/workspace metadata.
- If an old card cannot be completed because its judge requires implementation evidence, leave it blocked and detached. Finish the real replacement first; close the old card later using the replacement's exact verified evidence when appropriate.
- Avoid redundant final-review chains. One full-contract review plus one focused re-review for a narrow correction is sufficient when the focused reviewer explicitly inherits unaffected evidence from the full review.

## Native adapter test environment recovery

Verify optional adapter imports as well as pytest before declaring an environment usable: Discord requires real `discord.ui.View` and `Modal`. For a fresh Hermes dev venv, use the supported editable install (`uv pip install --python <venv>/bin/python -e '.[dev]'` plus pinned adapter dependencies); wheel/sdist builds are intentionally refused. A worker's headless approval failure may be handled by the coordinator's normal terminal approval path, never by suppressing warnings or relaxing security settings. Record actual native test results before resuming implementation; successful baseline tests are not full delivery acceptance.

- Invoke test files with full exact paths, never truncated with ellipsis or bracket characters — the runner misparses them as parametrization and collects zero tests. When a combined multi-file invocation errors, run each file individually and report per-file counts.

## Preserved-WIP handoff checklist

- Absolute workspace path recorded
- Current base SHA and branch recorded
- `git status` summarized without cleaning or stashing
- Checkpoint file read before edits
- Original worker stopped or blocked
- Continuation uses the same directory and no competing worker
- Final implementation commits one exact descendant; push only when the publication contract requires it
- Independent review uses an isolated checkout of that exact candidate; locally available commits are valid for a local-only contract

## Pitfalls

- Before resuming an implementation blocked on test dependencies, identify the complete acceptance-test dependency set, probe candidate interpreters for both the test runner and the actual platform SDK, then execute the relevant native tests through `HERMES_PYTHON='<absolute venv>/bin/python' scripts/run_tests.sh <focused tests>`. Inspect previously successful review environments and reuse them read-only when compatible. A passing generic approval suite proves only that suite works; it does not establish that Discord views/modals or another optional integration loaded. Record the stable interpreter, actual imports, pass/fail/skip counts and remaining coverage gaps before describing the environment as repaired. Never substitute skipped native tests, SDK stubs or bypassed package security checks for this proof.

- A worker running inside the gateway service cgroup must never stop or restart that same service; keep the release blocked and route the guarded stop/switch/start to an externally scoped interactive operator rather than wrapping the restart in a script to evade the safety gate, because the embedded worker is killed with its own service and the restart never verifies.
- Do not link first and inspect later; a wrong parent edge can instantly demote a runnable replacement to `todo`.
- When a worker crashes within a minute or two of spawn (nonzero exit, no heartbeat, no work claimed), read `~/.hermes/kanban/logs/<task>.log` before changing models or retrying — the tail usually names a startup refusal, and repeated blind retries just burn the failure budget until the card gives up.
- Do not interpret several duplicate cards as several defects; consolidate by underlying defect and reviewed SHA.
- Do not rerun a whole-app audit after a narrow final correction when a complete independent baseline already exists; require focused reproduction plus inherited unaffected evidence to avoid endless review loops.
- When a card's workspace provisioning is malformed, resolve the project in the **creating profile's** registry before resuming: registries can differ by profile, and an unresolved `project` can silently produce a scratch card even when the caller supplied an ID. Inspect the card's run, worker PID, worktree existence, downstream links and base SHA first. If a project-linked task was rejected **before worker start** solely because its manually supplied path is noncanonical, preserve the existing dependency graph: prefer a supported native workspace edit, or if unavailable make a conditional, narrowly scoped audited DB update on the inactive task to `<repo>/.worktrees/<task-id>` and read back the exact task and descendants before unblocking. Never rewrite a path that contains work or is held by a worker. If the project anchor is absent or a checkout has unique work, preserve that work and build one valid replacement from a profile that resolves the project; read back `project_id`, `workspace_kind`, path and dependency links before dispatch.
- Archive invalid scratch cards once their replacement is verified and no worker is active; a `dependency` block with no unmet parent can auto-promote and repeatedly reclaim the malformed card, and linking it to a temporary parent merely postpones the loop. Read back archived status so completing the parent cannot release the invalid card.
- Rewire with link-then-detach: link the verified replacement as parent of the downstream child, then detach the broken parent through the board's supported unlink surface. In worker contexts that forbid shelling out to `hermes kanban`, do not bypass that rule; if native unlink is absent, use a narrowly scoped, audited SQLite transaction only after verifying no task is running on those edges, and read back the exact parent list. If concurrent repair created duplicate cards, archive only the unused duplicates, detach only their added edges, and retain the already-running authoritative lane.
- When re-provisioning a whole dependency graph, recreate every parent link on the replacements and give each its own per-task worktree — missing links plus a shared checkout let downstream lanes claim early and collide in the same directory.
- Verify a forced skill is installed on the assignee profile before creating a task with it — list that profile's skills first and omit the ref if absent, because the dispatcher crash-loops on unknown skill gates.
- Never enable a data-training model tier without the owner's explicit consent: `-contributor`-suffixed models train on prompts and completions, and the worker refuses such overrides in non-interactive runs unless `security.allow_data_training_tiers_noninteractive` is set in every assignee profile's own config.yaml, not only the global one — spawned runs resolve settings from the assignee profile, so a global-only waiver leaves the other profiles refusing at startup with identical crash signatures. Offer the standard suffix-less variant (no training, no waiver) alongside the waiver option and let the owner choose; record the choice on the card. Confirm any config fix in the next spawn's log tail, since the write alone proves nothing.
- Set worker reasoning effort with `--reasoning LEVEL` (none, minimal, low, medium, high, xhigh, max, ultra) or persistently via `agent.reasoning_effort` in the assignee profile's config.yaml — it applies to subsequently spawned runs, so configure it before dispatching the lane, not after.
- When fresh task worktrees resolve to a stale base while the approved base has moved on, confirm the remote SHA and inspect each branch/worktree for unique commits and uncommitted files before changing it. Prefer creating an absent task branch at the approved SHA; if a branch/worktree already exists, obtain explicit scope-specific authorization before any destructive reset, and preserve untracked plans or worker output. An expired or denied command confirmation means the action did not happen: do not reframe general milestone approval as reset consent or pursue an equivalent action through another tool. Keep implementation and review gated until the authorized base is read back.
- When auto-decomposition produces path-less worktree children, inspect the child-insert path and the parent/board repository anchors before retrying dispatch. A project-less parent can have a valid Git worktree while its children inherit `worktree` but lose both path and project; preflight then cannot find a repo on a shared board. Fix the creator to validate a real repo anchor and assign each child its own canonical worktree path and branch atomically; if no anchor is verifiable, leave the parent in triage without partial children or a decomposition event. Before fan-out, compare an existing linked parent checkout with its effective branch (`branch_name` or `wt/<parent-id>` when NULL); the dispatch preflight enforces that fallback, so skipping the check can publish children behind an unlaunchable parent. Test multiple siblings, missing anchors, wrong-checkout/NULL-branch parents, and project-bound parents. Do not set a board default workdir to repair one project's cards — it would route other projects into that repo. Distinguish auto-decomposition from a regular `create_task` child using `creator_task_id`; that provenance alone does not convey workspace authority, so repair the separate call site with explicit project/workspace input rather than assuming the decomposition fix covers it.
- When creating a project-linked `worktree` task, omit `workspace_path` and let the dispatcher provision the canonical `<repo>/.worktrees/<task-id>` — a caller-supplied path fails preflight because the guard requires the path to be canonical and task-owned.
- When dispatch preflight reports a task worktree target checked out on another branch, inspect `git worktree list --porcelain`, the target's `git status --short --branch`/HEAD and the expected branch ref before acting. For a truly stale duplicate with no worker and no unique work, remove it and unblock for re-provisioning. For a live clean checkout holding the intended candidate or preserved WIP, do not delete/reset it: if the expected branch ref is unused and stale, rename that ref to an archive name, then rename the active branch to the dispatcher-expected name (or attach a detached exact HEAD with `git switch -c <expected-branch>`); verify status, HEAD and exact ancestry, comment the administrative repair, and unblock. Never erase uncommitted files or claim that changing a branch name reviewed the candidate. Require matching remote evidence only for a publication contract; local-only review does not require a push.
- When two independent verdicts disagree on one SHA, the verdict with concrete file:line evidence wins; route rework from it and record the shallower approval as superseded instead of averaging them.
- After `unblock` or `promote`, read the card back: an unblock that errors 'not blocked' means the state already moved (e.g. a guard set it to `todo`) — re-read instead of retrying, then advance a `todo` card with satisfied parents via `dispatch` or `promote`.
- When a fully verified card sits in triage and both `complete` (stale run / already terminal) and `unblock` (not blocked) refuse it, stop after one repair attempt: fix the underlying preflight cause if one exists (e.g. fast-forward a stale task-owned branch to the verified SHA), record the DONE handoff with evidence in the durable project dossier and the originating chat, and report the board state honestly as administrative-only — repeated complete/unblock retries never clear a triage lock.
- When a card stalls at handoff with implementation claimed complete, inspect its completion contract and verify the candidate before re-dispatching. For local-only delivery, confirm the exact commit with `git cat-file -t <sha>` in the review repository, prepare the review task's own clean branch at that SHA if the ref is absent, and read back its HEAD/ancestry before dispatch. Worktrees in the same Git repository share local objects; a fresh checkout at a stale base does not justify pushing an unreviewed candidate. For a genuinely separate clone, transfer the exact commit through an authorized local or publication mechanism and verify it there; push only if the publication contract or owner authorization permits it. For a publication contract, verify the exact remote branch/PR head before advancing review.
