# Remote Messaging Integration Delivery

Deliver Discord, WhatsApp, or similar Hermes remote-control channels as private, end-to-end verified interfaces. For Thomas, work quietly and report the final working product; do not narrate diagnostics, commands, internal handoffs, or repeated progress updates.

## Procedure

1. **Choose the operating mode before setup.** Determine whether the platform uses a dedicated bot identity or Thomas's personal account. A dedicated WhatsApp bot requires a second WhatsApp account/number; when only one number exists, select self-chat mode before generating the QR. Explain only the consequential choice, then proceed.
2. **Establish one owner.** Attach each bot credential only to the default coordinator profile. Keep specialists behind coordinator/Kanban rather than copying one platform credential into every profile.
3. **Restrict ingress.** Configure immutable Thomas-only user/chat identifiers, disable allow-all and public-group control, and keep unknown DMs ignored or pairing-gated. Under a multiplexed gateway, verify the profile-scoped authorization source actually read at runtime; a top-level compatibility value may not be the effective gate.
4. **Pair interactively.** When Thomas must scan a QR or approve a linked device, present exactly one action and keep the pairing process alive. Never place phone numbers, QR payloads, tokens, or private routing IDs in chat, task cards, reports, or memory.
5. **Honor the current interruption policy.** For Thomas, Discord is decision-only: suppress unsolicited progress, completion, retry, review, cron/background and restart/online/offline notices rather than relocating them to an updates/home channel. Keep directly requested replies and genuinely necessary critical decision/required-human-action requests. Require real Approve / Niet approve / Tegenargument controls, with counterargument free text returned to the originating manager without approval. A SOUL policy is not proof of runtime filtering or button support; trace all egress paths and verify the real adapter. Only use separate routine updates/home delivery for users who explicitly request it.
6. **Verify the real path and silence.** Use a genuine Thomas-originated request to verify inbound authorization and read back its grounded reply; never impersonate his identity for a live test. For decision-only operation, verify an explicitly agreed harmless decision prompt rather than sending a routine test notice. Exercise routine completion, internal blocker, retry and lifecycle events through the real notification dispatcher with a recording transport and assert no Discord send while internal/desktop records remain. Trace automated board subscriptions and home-channel fallbacks separately: instructions on task cards cannot suppress gateway-generated notices. Do not claim silence is active until the filtering code/configuration is deployed and verified. A checkmark reaction, typing indicator, connected socket, configured flag, or service health alone is not success.
7. **Verify the request is raised before testing its buttons.** Compare live task blockers with the decision ledger by state and origin, then trace a real blocked task through the internal manager wake, manager assessment and supported request entry point before the outbox. A connected bot and successful synthetic clicks prove only transport/callbacks: a delivery loop that reads already-pending records cannot create the missing business request, and not every `needs_input` blocker warrants a Discord DM. Require owner/request-ID/action/scope-bound, expiring, single-use approval behavior. Reject generic affirmatives and unqualified approval commands. For Thomas, verify all three real controls: Approve authorizes only the displayed proposal once; Niet approve leaves it unapproved; Tegenargument opens a text modal and returns feedback durably to the originating manager/task without authorization. Exercise cancellation, expiry, replay, concurrent prompts and wrong-owner clicks; a materially revised proposal needs a fresh request. Include a Desktop- or Kanban-originated decision, because a command approval initiated inside Discord does not prove cross-channel continuation. Enforce exact-operation consent across every model-accessible execution path, not just the terminal tool: test alternative Python execution, registry dispatch, inline tools and connector/bridge calls before treating a one-shot command grant as secure. Preserve normal policy for unrelated tasks and do not treat business consent as executable authority. Follow the raise → deliver → resolve → consume/steer boundary matrix in [Decision workflow verification](references/decision-workflow-verification.md). A saved outcome or task comment alone does not prove the correct manager/worker consumes it; explicitly distinguish durable task steering from a new message injected into a live Desktop conversation. Use actual SDK views/modals in automated tests, report optional-dependency skips as uncovered, and exercise only a harmless synthetic decision during live activation.
8. **Activate the reviewed code and configuration together, then verify coexistence.** A restart does not deploy a candidate. From the authorized external release context, preserve a restorable snapshot, stop the gateway and verify no service PID, switch the installed source to the exact reviewed clean revision, apply the required settings through the supported configuration CLI, and read back both raw and effective configuration before starting once. Verify the new PID, installed source revision and real transport receipts; recheck other enabled integrations without changing their authorization. Follow the activation checklist in [Decision workflow verification](references/decision-workflow-verification.md). Respect already-granted activation permission: do not ask again after merely restarting the old code. When Thomas explicitly authorizes proceeding despite active workers, follow the supported shutdown/recovery path instead of silently reinstating the idle-worker prerequisite; that authorization does not waive backup, security or verification gates.
9. **Report only the verified result.** Tell Thomas what is active and, if unavoidable, the one action he must perform. On a status request, distinguish queued, running, code-approved, activated and live-verified; a blocked release card is not automatically progressing. Do not promise an automatic next step without an actual continuation mechanism. Do not claim connected from service health or an SDK import warning, and do not call an omitted deployment step a technical blocker. Correct unsupported earlier claims directly. Give an estimate only with grounded remaining work and queue assumptions, not repeated optimistic countdowns.

## Pitfalls

- Decide dedicated-bot versus self-chat mode before launching setup, because pairing the wrong account creates a linked session with no reachable bot conversation.
- Inspect fresh gateway logs after each real test message, because adapters may react or show typing before the central authorization layer rejects the sender.
- Verify the effective profile-scoped allowlist under multiplexing, because configuration readback can show the intended value while runtime scope omits it.
- Attribute multiplexed startup warnings and scheduled-job delivery errors to the actual process and route before changing configuration: a standalone cron sender can fail independently of a connected default gateway, while a disabled specialist adapter can coexist with a healthy default adapter. Read effective default configuration and verify the failing route's real delivery rather than changing credentials or repeatedly restarting on one ambiguous log line.
- Do not treat a malformed auto-decomposition subtree as delivery progress; detach workspace-less cards and continue through one authoritative project-pinned or scratch lane.
