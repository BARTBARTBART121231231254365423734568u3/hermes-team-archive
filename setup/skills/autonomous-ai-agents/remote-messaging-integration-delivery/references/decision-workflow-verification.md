# Decision workflow verification

Use when a messaging integration must carry approval or counterargument between a manager, background task and private chat. This is an acceptance recipe, not a claim that an installed adapter already implements these boundaries.

## Procedure

1. **Fix the proposal and origin before testing.** Choose a harmless operation and capture its exact task, manager profile, originating session, action, scope and version. Bind the authorized owner and private destination from trusted configuration, not proposal text. Keep unrelated tasks runnable.
2. **Exercise each boundary through its real entry point.** Use the manager's actual supported request mechanism, the persistent store, the delivery dispatcher, SDK callbacks and the consumer. A helper returning an approved object is not an end-to-end test.
3. **Separate local transport simulation from live receipts.** Native SDK View/Modal objects with a recording DM prove callback logic, not Discord delivery or a human click. Use real transport only in the authorized live-verification phase; never fabricate or impersonate the owner's interaction.
4. **Attach evidence to the exact candidate.** Record the SHA for each suite and distinguish broad coverage from focused post-change reruns. When a rehearsal depends on a separately reviewed recovery module, make its normal CI mode fail closed if that module is absent or imported from another checkout; allow a clearly named base-only mode for diagnostics, never as a passing integration gate. Include negative controls for both absent and foreign-checkout imports, then run the full rehearsal against the assembled candidate. If the final commit changes executable behavior, rerun its impacted integration paths; a broad result from an ancestor does not cover those changes. Remove temporary debug logging before review — a debug commit is not a releasable candidate. Do not add overlapping suite counts into a purported unique-test total.
5. **Release through existing gates.** Assemble separately reviewed blocker-recovery and decision-delivery changes on one clean checkout based on the current installed source; run exact-head CI and independent security review of the assembled behavior before activation. A GO for a rehearsal gate or a separate local candidate is not a GO for their integration, restart or live owner DM. Keep known baseline failures separate only when reproduced on a clean baseline and confirmed not to invalidate this outcome. Document supported execution targets and limitations rather than quietly treating a local-command proof as authorization for arbitrary remote or business APIs.

## Reviewed gateway activation and live receipts

1. **Resolve the actual release target.** Read the release manifest, `readlink -f <installed-source>` and `git -C <installed-source> rev-parse HEAD`; compare with the independent review's exact SHA and clean candidate. A successful `gateway restart` reloads the installed source, not whichever branch was just reviewed. If the shared worktree advanced mid-release, STOP: the approval no longer matches live state, and re-pointing the symlink at the same mutable worktree is not a rollback — require a fresh exact-SHA checkout or re-review before proceeding.
2. **Use an external maintenance context.** Inspect `/proc/self/cgroup` before stopping systemd: a child inside the gateway service can be killed by its own restart. Preserve the old symlink target and configuration privately, and use SQLite's `Connection.backup()` API with an integrity check for a consistent database snapshot; copying only the main DB file can omit WAL transactions. Keep user-approved worker interruption separate from permission to discard work.
3. **Stop, switch, configure, start.** Use the supported service lifecycle command and verify `MainPID=0`. A stopped unit can report `failed` after a shutdown timeout; distinguish that from a still-running process before deciding whether source/config writes are safe. Atomically replace the installed symlink with the exact reviewed candidate, apply settings using `hermes -p default config set`, and read back `gateway.config.load_gateway_config()` in a fresh interpreter. Cancel superseded pending decisions before stopping, so recovery cannot re-arm a stale card next to its replacement. For decision-only delivery, verify enabled transport, `notification_policy=decisions_only`, and string-valued owner/private-DM bindings without printing identifiers. Do not alter unrelated integration settings. Start once, read the new PID and source revision back, and keep rollback scoped to source/config rather than overwriting the live board.
4. **Prove delivery using the real dispatcher.** Create one explicitly harmless dedicated test task and raise its immutable proposal through the supported manager entry point. Capture its full request ID privately and use it for every later ledger query — prefix lookup is unsupported. Let the gateway outbox deliver it; do not replace this with a direct REST send, which bypasses the path under test. Read the ledger's delivery state and fetch the actual Discord message. Verify the bot author, private recipient, exact proposal, native component labels `Approve`, `Niet approve`, `Tegenargument`, component custom-ID binding to request/version/digest, and enabled (not disabled) state via the channel-messages readback. Do not resend a pending test just because a later session needs to inspect it.
5. **Separate activation from owner interaction.** Record code/config activation and real message delivery as independently verified facts. Ask Thomas for one harmless click/modal submission only when it is the remaining irreducible check. Never simulate his identity, infer a click from successful delivery, or claim the silence matrix was exercised merely because the policy loaded. After every gateway restart, confirm pending controls were re-attached through the recover path before asking the owner to click; a restarted process rejects clicks on pre-restart cards until recovery runs. When the owner reports a click was rejected, add temporary deny-debug logging, capture exactly one failing click, then remove the debug commit before review — a debug commit is never a releasable candidate. Read the persisted outcome and correct task continuation after the interaction before claiming that boundary passed.

## Boundary matrix

| Boundary | Required behavioral evidence | Failure case |
| --- | --- | --- |
| Raise | Real manager entry in true default-manager runtime creates one immutable record for the intended task/issue/version | Specialist impersonation, delegated-child context, duplicate issue/version with changed material, or proposal-supplied owner cannot create authority; a manager-only entry run from a delegated child fails closed even for read-only show |
| Deliver | Outbox invokes the configured manager adapter and verified private recipient; full displayed action/scope matches stored material; the send registers the persistent interaction handler so the controls are actionable, not merely visible | Wrong profile, public fallback, wrong DM recipient, unavailable delivery, or a send without handler registration leaves the operation paused; a `delivered` ledger state alone never proves clickability |
| Resolve | Actual SDK controls validate owner, destination, original message, request/version and outstanding state before atomic resolution. When the interaction carries no channel object (notably modal submits) or the recovered persistent view lost its in-memory message after restart, resolve the verified owner DM via the interaction-channel resolver then the stored channel ID — never any other channel — and validate destination against it; the owner, message, request/version and outstanding-state checks still apply. discord.py DM shapes vary per event: cached DMs expose the owner in `recipients`, while uncached or interaction-delivered DMs may expose only the bot itself — accept the bot-only shape only when the channel id matches the configured owner DM, and keep rejecting a recipients list containing neither bot nor owner. | Out-of-order, copied, duplicate, stale and wrong-owner clicks cannot approve another request |
| Approve → consume | The correct originating worker/manager consumes the exact approval once and a harmless actual side effect occurs once | Crash or ambiguous result after consumption must not silently retry the operation |
| Deny → continuation | Original sensitive operation remains unapproved; outcome is observable through the real manager/task continuation path | A saved denial must not make the blocked operation eligible through a generic affirmative or stale grant |
| Counterargument → steering | Opening/cancelling the modal does nothing; submitting routes text to the right manager/task and that consumer can actually retrieve it | Text storage alone does not prove a live Desktop turn, automatic replanning or resumed work; test and report the supported behavior precisely |
| Recovery | Restart restores pending record and controls on the verified original message, or safely leaves it paused. After every gateway restart, confirm pending controls were re-attached through the recover path before asking the owner to click; a restarted process rejects clicks on pre-restart cards until recovery runs | Ambiguous delivery is reconciled without blindly resending; recovery never manufactures approval |
| Silence | Routine dispatcher events produce zero Discord sends while internal records remain; the same adapter still delivers solicited replies and genuine decision prompts | Critical-looking words, arbitrary metadata, media routes and home-channel fallbacks cannot bypass the filter |

## Keep authorization narrow

A business approval records consent for the displayed business decision; it is not a universal credential or shell grant. A terminal approval must bind command bytes, execution target and working directory at the real execution boundary. A revised proposal requires a fresh decision. Counterargument is steering, never consent.

## Verify execution authority across tool paths

1. **Inventory execution entry points before approving the design.** Trace the shared registry, bridge/connector dispatch, inline executors, direct `execute_code` path and terminal path. A guard inside `terminal_tool` alone cannot enforce a task-wide restriction when the same worker can launch a subprocess through Python or invoke another effectful tool.
2. **Reproduce the bypass with a harmless real effect.** Reserve a dedicated exact-command decision, then attempt a different command through the actual Python execution entry point. Require refusal before that subprocess runs; merely checking that a guard helper returns false misses dispatch and unattended-approval fast paths.
3. **Apply a fail-closed dedicated-task boundary before permissive shortcuts.** Permit only the displayed terminal operation once and the explicitly required same-task lifecycle/handoff tools. Deny alternative execution, connectors, process stdin, file mutation, scheduling and unknown future tools for that dedicated task. Validate target task and board for allowed handoff calls; a missing decision store must not silently create an empty store and regain normal execution.
4. **Test every decision state and preserve ordinary work.** Exercise pending, denied, counterargument, expired, cancelled, approved and consumed records. Alternative routes must remain denied without spending the legitimate grant. Separately prove exact command/cwd/target one-shot consumption and replay rejection. For ordinary tasks and business-only decisions, verify that existing approval policy still applies; business consent must not override an independent deny policy.
5. **State the boundary honestly.** A model-tool guard is not an operating-system sandbox. Approved script contents and trusted plugin implementations remain within the documented trust boundary; do not claim arbitrary-process containment or complete security from local regression tests. Route the corrected exact revision through independent review before activation.

Keep brief fields complete within platform limits: reject an oversized proposal rather than truncating the authority the owner sees. Render the owner-facing card human-readable with an issue-project title plus a short body stating what is happening and which answer is needed (recommendation, why-owner, impact, exact action, scope, no-response behavior); keep request/version/digest binding in component custom IDs plus SQLite only, never in visible text and never as raw JSON. Redact or reject secrets before persistence and rendering, not only in the final report.
