# Cloud access for agents

Use this workflow when the user wants an agent to inspect or change resources in a cloud account. Treat the requested cloud visibility, write authority, billing authority, production impact, and which **agent profile** receives access as separate decisions.

1. **Translate the request into an authority matrix before touching credentials.** Record account/organization/project coverage, data visibility, permitted read actions, narrowly permitted writes, explicitly forbidden IAM/billing/provisioning/scale/deletion actions, and approval triggers. If the user permits writes only when they are free, do not interpret that as general edit rights: a change to an existing workload or even a query may consume paid resources. Default an unclassifiable action to pause-and-ask, not 'probably free'. Preserve independent production/release gates.
2. **Inventory without exposing secrets.** Check the installed CLI, profile-local connector list, presence (not contents) of credential files/environment variable *names*, and the chosen account/project identifiers. Resolve a user-given project *display name* to the cloud provider's immutable project ID through already-authorized discovery; inspect local project references only as candidates, not proof of cloud scope. Never substitute an identically named repository or another provider's project ID. If no authorized discovery exists, request just the exact project ID from the owner's console before configuring IAM or a connector. Never paste tokens into chat, cards, memory, or plaintext tool configuration. Do not silently use the owner's existing administrator login; its permissions and audit attribution would extend to the agent.
3. **Choose credential isolation and least privilege before login.** Prefer a distinct machine/agent identity, short-lived refreshable credentials, and explicit per-project permissions; rule out long-lived service-account JSON keys unless a reviewed alternative truly cannot work. Verify whether profiles actually share OS identity/filesystem/ambient tokens and passwordless privilege escalation—profile-local configuration or a second local UID is not a security boundary if another agent can read credentials or become root. If isolation cannot be proven, keep broad owner credentials off the host; either isolate the whole agent runtime behind a boundary other profiles cannot administer, or ask the owner to explicitly accept the residual cross-profile risk for a tightly scoped read-only identity. Record exactly which risk was accepted; it does not approve a specific IAM grant, new cost, or write authority.
4. **Verify the connector against current vendor documentation.** For Google Cloud, separate Hermes MCP client compatibility from the Google Cloud service endpoint, identity, project IAM, enabled APIs, and `mcp.tools.call` permission. Hermes registration alone does not grant access; Google's `roles/mcp.toolUser` enables MCP calls but is not a substitute for the product permissions. See `references/google-cloud-mcp.md` when Google Cloud is the target. Read the current Hermes and provider docs and CLI help before selecting auth flags or installing software.
5. **Stage reads, then narrowly scoped writes.** Obtain the owner's specific approval for consequential IAM/API/billing changes before applying them. Acknowledging a shared-host risk or consenting to a one-time browser bootstrap is not authorization to create a principal, change IAM, or store a personal refresh token. First establish a refreshable, genuinely implementable identity path; one-time owner login alone cannot authenticate unattended calls. Grant/test bounded project metadata reads only after checking the exact API's pricing and enabled state; do not use BigQuery/AI queries as a 'read-only' smoke test. Add only individually reviewed low-risk write capabilities after read access works; avoid blanket Editor/Owner roles, generic write-capable MCP toolsets, and terminal/CLI bypasses. Test a deliberately forbidden operation without actually mutating a resource, by inspecting effective permission/policy rather than issuing a dangerous call.
6. **Verify the real boundary and report honestly.** Re-read the exact IAM/config target, show which projects and tools the agent can actually list/read, check access from an unauthorized profile where safely possible, and verify refresh/restart behavior. Separate configured, authenticated, read-verified, write-verified, and still approval-gated states. A budget alert is not a hard cap; never promise zero spending based on alerts, prompt rules, or a tool-name filter alone. Ask the owner only for a concrete missing identity/authorization decision once safe independent investigation is exhausted.
