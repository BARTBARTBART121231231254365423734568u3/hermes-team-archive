# Live preview delivery

## Procedure

1. Prefer Hermes Desktop's native browser-preview pane for immediate review. Open the exact built site or localhost dev-server URL in the initiating user's window, then read back the rendered title, URL **and target-specific content**; an `open` success or HTTP 200 alone does not prove the correct tab rendered. If the pane read still reports an earlier page/tab, treat the new preview as **not delivered**: close all preview tabs, reopen the requested page on a distinct URL (a harmless cache-busting query is enough), and read back the exact title, URL, and requested page text before claiming success. A returned `open` URL can coexist with a stale selected tab; only the pane readback proves what Thomas can actually see. Match host/path, title, AND page-specific text against the requested page: a healthy `kind: url` readback showing an unrelated title (e.g. another product's login/auth page from a different process) means the pane is displaying a foreign tab, not your page — close all tabs and reopen on a distinct URL until all three agree. When Thomas asks for the in-browser Hermes preview, do not substitute `MEDIA:`, `::preview`, a screenshot, or a download; those are different surfaces. If opening a file path cannot be read back but the identical artifact has a healthy local HTTP route, open that route and verify the pane. If the native pane still cannot show the requested page, state the blocker plainly rather than calling a fallback the requested preview.
2. Verify the rendered UI, not merely the file: inventory interactive elements first, then exercise representative navigation, buttons, and form flows in the preview rail. Before presenting a changed site, compare the exact preview artifact with the user's requested changes page by page; open policy/footer pages and admin entry points, not just the homepage. A static admin mock is not evidence that a protected dashboard or product wizard works: either demonstrate the real authenticated flow safely in a local browser, or provide a clearly labeled, visually faithful, interactive, read-only snapshot of the new screens without sessions, secrets, or customer data. Reject a preview whose visible admin still shows old tables while the new features exist only behind an unshown login. Render secondary pages at desktop and mobile widths and inspect typography, links, panels, and spacing against the chosen site theme; passing tests and HTTP 200 do not establish visual fidelity. For a responsive order dashboard, assert mutually exclusive table/card visibility at and around the breakpoint (and that the overview table remains visible where intended), because a desktop table can remain displayed underneath mobile cards even while all content tests pass. For a static export, serve the built directory itself (not only the dynamic app); click product/detail links and check that form actions resolve within the export, since rewritten app routes can 404 on a static server. For collection filters, run combined sequences—select two facets, submit search, change sort, then reset—and assert every selected facet survives each GET roundtrip without duplicate query keys and that the resulting cards match the controls. Isolated filter/search tests miss form submissions that silently drop earlier selections. Report only interactions actually performed; if a real browser is unavailable, label an HTTP plus DOM/JS harness as such rather than claiming visual browser QA.
3. When work comes from a separate designer/coder task, require its handoff to include the durable preview target: absolute HTML/build path or localhost URL, generating branch/commit, plus how it was built. Cite claimed screenshots only as absolute host paths verified present on the host first — a reviewer without render tools stays blocked on bare filenames. Before opening it, compare the preview's source commit with the implementation and any newer correction branches; a locally healthy preview can still be an older build that hides the requested changes. If the producing worktree or branch was removed after completion, re-materialize the exact commit read-only (`git worktree add --detach`) and serve its built preview directory — the commit object survives branch cleanup. The coordinator opens the exact candidate in the user's current window because preview panes are session/window scoped. If the preview deliberately omits an authenticated editor, label that limitation in the browser itself and in the handoff, then show the actual protected flow in a safe local session before claiming editing works.
4. For phone or external-browser review, publish only through a configured HTTPS route. If the user requests a permanent staging URL instead of expiring preview links, preserve the same preview isolation: deploy only an audited static build directory, not the application's full server merely because staging credentials exist. Public admin login, writable APIs, and file-backed state need their own security gate (vetted identity/MFA and durable storage); an environment named `production` or `staging` grants neither. Require the deployed artifact to contain only public assets, reject non-GET/HEAD and source/API paths, verify the service's actual source branch and start command, and probe both allowed and forbidden routes on the live URL. For the ordinary preview publisher, scope the public proxy to `/preview` rather than `/`, keeping health/status endpoints localhost-only. First verify the route configuration, then publish a smoke-test page, fetch the returned URL over HTTPS, and open the rendered page before sharing it. When the public route serves the build under a subpath, root-absolute asset references (`/assets`, `/icons`) 404 and the page renders blank: verify per-asset-class status codes after publishing, and if the build cannot be rebuilt with the subpath base, publish a rewritten copy with relativized references clearly labeled layout-check-only (static, no backend) — never as the acceptance candidate. Tailscale Funnel/serve config persists in daemon prefs, so with the daemon enabled at boot no extra keepalive service is needed; verify after a reboot instead of building one.
5. Publish through the normal on-demand preview script when it exists rather than manually starting preview infrastructure. Locate the script on the active host first, then invoke it with that host's working Python interpreter: `<python> <create_preview.py> <site-dir-or-html-file>`. It should health-check and start/reuse the lightweight localhost server and, when an HTTPS base is configured, verify the public route before printing the URL. Do not create a login service or run a local model for preview delivery.

   Invocation facts that cost a cycle each if guessed:
   - Do not hard-code an operating-system path or interpreter name; resolve both on the live host before invoking the script. The same applies to helper binaries the publisher shells out to (tunnel CLIs and the like): resolve via environment, then PATH, then platform default — a hardcoded path from another OS fails the readiness check and looks like missing infrastructure.
   - The script takes exactly one positional path and has no flags; `--help` may be parsed as the path rather than documentation.
   - Point it at a directory containing `index.html`. Publishing a bare directory of assets can succeed while the preview root 404s — only exact filenames are reachable. Write a small `index.html` linking the artifacts before publishing a screenshot/asset folder.
   - Treat a returned `localhost` or loopback URL as host-local evidence, not a link for Thomas. A local HTTP 200 does not establish phone/other-device reachability; share externally only after a configured HTTPS URL is fetched successfully from outside the local origin. For in-app review, open and read back the page in the initiating Desktop preview pane instead of asking Thomas to click the loopback link.

6. Before declaring preview tooling unavailable, search the active Hermes home and project tooling directories for the publisher. Always-on migration notes can be stale; the filesystem is the authority, and skipping this check pushes the session into inventing delivery workarounds for tooling that already exists.

7. When the user reports a published URL does not work, triage the stack before republishing or switching delivery methods:
   - `curl -sS -m 5 http://127.0.0.1:8080/healthz` — expect `ok`.
   - `tailscale funnel status` — expect the host with `Funnel on` and `/preview proxy http://127.0.0.1:8080`.
   - `curl -sS -o /dev/null -w '%{http_code}' <full-url>` — read the status code only. curl exit 23 (`client returned ERROR on write`) is a local stdout-write artifact of the captured terminal, not a server failure; a printed `200` alongside it means the server served the asset correctly.
   - If the port accepts connections but health returns an empty reply and HTTPS returns `502`, identify the listener with `cmd.exe /c "netstat -ano | findstr :8080"`, terminate only that stale PID, verify the listener released the port, then rerun `create_preview.py` against the original artifact. In the Git Bash/MSYS terminal, prefer `python -c "import os, signal; os.kill(<PID>, signal.SIGTERM)"` over hand-quoted `taskkill`: MSYS argument conversion can corrupt `/PID`, `/F`, or quoted filter arguments. The tunnel can remain healthy while a wedged local publisher owns the port, and the publisher cannot self-recover until that listener is released.
   - After republishing, require both localhost health `ok` and public HTTP `200`, then open the exact local `index.html` in `desktop_preview` as an immediate in-app fallback while sharing the newly verified public URL. Treat a printed `200` plus curl exit 23 as success only when the status code was emitted—the exit is caused by the captured output sink closing, not by the server.
   If all three initial probes pass, the failure is client-side (browser, DNS, or the chat surface), not the preview stack. Ask for the exact observed symptom — blank page, error text, spinner, immediate failure — and fix from that, rather than generating another delivery format.
8. Use opaque, non-project-identifying preview IDs. Serve only the preview root and static assets; reject source-tree symlinks/reparse points, traversal, metadata files, malformed IDs, and directory listings. Validate every configured public base, including fallback configuration, as credential-free HTTPS with no query or fragment. Retain previews under the declared cleanup policy.
9. In the final handoff, provide either the verified native preview target or a verified clickable HTTPS URL, state what interaction was tested, and clearly label any remaining external-sharing limitation. When asked whether another person can view it, distinguish three modes explicitly: in-app preview (current Desktop window only), standalone HTML attachment (recipient downloads and opens locally), and externally shareable HTTPS link (only after an independent public fetch succeeds). Never answer that a local preview can be shared by forwarding its loopback URL. **When the request is for a document as a file, switch delivery mode:** attach the validated source file itself, not an HTML rendering of it or a plain path; for a `MEDIA:` handoff use a simple attachment path and verify a copied artifact is byte-identical before posting it. A preview of the specification must be labeled as documentation, not as a functioning app. If the user asks for the file after a preview misfires, send the file immediately instead of debugging another preview surface.

## Pitfalls

- Serve the original built directory for an in-browser site review; do not replace it with an improvised single-file router merely to make assets portable. Reimplementing navigation or filters in a wrapper changes the artifact under review and can conceal defects in the actual app. Use standalone HTML only when the user requests a downloadable/offline artifact, and compare its interactions with the original before delivery.
- When a standalone HTML or `::preview` is the fallback, make it genuinely standalone: inline its CSS, scripts, and image assets (e.g. SVG data URIs), and preserve navigation/interaction for the pages promised. An `index.html` attachment with relative `style.css`, `app.js`, or image links can render as unstyled text when detached from its build directory. Assemble the single file with the source document head intact — extracting body sections only silently drops the `<style>` block and ships an unstyled page. Do not carry page markup inside JSON-escaped JavaScript strings; leaked `\n`/`\uXXXX` sequences render literally instead of decoding. Do not execute the demo's own scripts through `new Function`/eval in a wrapper; include or serve them statically instead. Render the exact delivered artifact in a real browser at desktop and mobile widths, inspect screenshots for layout and missing assets, then exercise a representative navigation/filter path before calling it a preview. Do not mistake a browser screenshot for the deliverable; it is verification evidence for the interactive HTML.
- When a published app sticks on its loading indicator with failing data fetches, the build is fine but its backend is unreachable from the preview origin — do not rebuild or cycle delivery formats; an app that fetches everything from its API never resolves in a static preview, so route a live-backend preview instead and screenshot the stuck state once as evidence.
- Do not substitute screenshots for a live-preview request; screenshots cannot demonstrate interaction or responsive behavior. If screenshots are the only available review evidence, label each one as full-page, viewport, crop, or isolated-state capture, and state which established regions are outside the frame so absence is not mistaken for removal.
- Stop after the second failed delivery attempt and ask for the concrete client-side error instead of trying a third format. Cycling through preview URL → inline image → copied file → base64 → prose description burns the user's patience without ever isolating the cause, and each new format can fail for a different reason than the last, so nothing is learned. Treat `::preview{file=...}` as another unverified rendering surface: do not present it as the fix after the preview pane and file attachment have failed unless its actual render and linked assets were independently checked.
- When a worker-produced artifact must reach the user and the live URL is in doubt, have the producing task declare the file in `kanban_complete(artifacts=[<absolute paths>])`. That path uploads through the notifier as a real attachment; paths mentioned only in prose, `metadata`, or chat text do not. Ask for this in the task brief up front rather than hunting for the file afterward.
- Do not delegate a new card to solve a delivery problem you can probe directly in one or two commands. Health-check, funnel status, and an HTTP status code are faster than a dispatcher cycle, and a child worker cannot see the user's browser either.
- Do not claim a preview publisher creates a shareable link just because it prints a URL; verify that its configured base is externally reachable over HTTPS.
- Do not make designers or coders run server or tunnel commands before publishing; use the on-demand publisher and treat a readiness failure as the actionable infrastructure error.
- Do not assume a background worker can open the initiating user's preview rail; the pane belongs to the active Desktop window, so surface the target to the coordinator instead.
- Do not expose a local preview server publicly until static-file containment, no-listing behavior, source-link rejection, and path-scoped proxy routing are tested; preview trees may contain metadata or paths not intended for delivery.
- Do not treat a detached launcher as durable until its server PID and health endpoint still succeed from an independent process after the launcher exits; worker job teardown can otherwise silently turn public previews into gateway errors.
- Treat same-origin previews with active script content as an intentional tradeoff, not isolation: do not publish mutually untrusted pages on the shared preview origin without a sandboxing/isolation design.
- When successive builds each publish a preview link, present exactly one current link and label earlier ones superseded with the commit each serves; the user otherwise opens a stale build on a second device and reports already-fixed behavior as broken. Re-verify which commit each link serves before claiming currency: fetch every URL and grep the served document for a build-unique marker — the new bundle filename hash from `dist/` or a copy string that exists only in the new build — then compare old versus new output. HTTP 200 on both links proves nothing about which build each serves.
- Reclaim a stuck local preview port by exact PID only after verifying process ownership via the listener's cwd/cmdline; a pattern-based kill can match your own shell command and terminate your session instead. Confirm the port is released before republishing.
