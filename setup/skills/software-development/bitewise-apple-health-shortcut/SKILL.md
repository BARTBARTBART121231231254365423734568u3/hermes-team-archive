# BiteWise Apple Health via Shortcuts

## Product boundary

- Keep BiteWise normal for every user. Apple Health is a strictly optional, opt-in connection only under **Settings → Connections**.
- Never require an iPhone, Apple Watch, Shortcuts, or a Health connection for signup, food logging, Wellness access, or another existing flow.
- Preserve the existing Wellness design, cards, hierarchy, route, and responsive layout. Wire Apple data into the current cards and existing source/freshness affordances; do not create an Apple-specific dashboard or redesign the page. Store Apple-only metrics without inventing new cards unless separately approved.
- Integrate directly into BiteWise's existing source-agnostic `wellness_data`; use `source = 'apple_health'` and the established metric names rather than creating a satellite service, separate database, or parallel health model.
- Treat stored data semantics separately from disconnected presentation: unavailable readings remain absent/null in `wellness_data` even if the existing disconnected dashboard intentionally renders zero-state placeholders.
- Make Apple Watch connection management and credential issuance available automatically to every existing and future authenticated BiteWise account. Do not maintain a static user-ID eligibility list; account authentication is the access gate.
- Preserve the per-user security boundary even when availability is universal: each signed-in user generates, rotates, and revokes only their own write-only Shortcut credential; store only its hash, show the plaintext once, and keep all uploads and Wellness reads owner-scoped. Never introduce a shared/global key.
- Treat account-creation policy separately from integration eligibility. Universal Apple Health access must not silently enable public registration; it means every account can connect after that account exists and logs in.

## Shortcut distribution and safety

- A user’s Shortcut uses a per-user, write-only, revocable ingest credential. It must not read BiteWise data or use a session/database credential.
- Build/share the shortcut through iCloud with an Import Question for the token; real iPhone testing proved this can install without a Mac. Build the working Shortcut once, then share it—do not make each pilot user manually reconstruct a multi-action payload.
- Never place real tokens, raw health data, Apple IDs, or personalized iCloud links in task cards, artifacts, or chat.
- In `Find Health Samples`, keep **Fill Missing OFF**. Missing Apple observations must stay missing/null, never become fabricated zeroes.
- Treat a token displayed in a screenshot as compromised: recommend revocation/rotation once without repeating the warning; if the user explicitly chooses to continue, keep progressing through the non-destructive Shortcut build without copying or restating the token.

## iPhone Shortcut authoring

1. Design the pilot endpoint before asking anyone to build a Shortcut. For a small pilot, prefer a minimal request containing only supported aggregate values (for example Steps and optional Active Energy), but preserve a validated device-local calendar day and UTC offset whenever the client/exporter supplies them. Never overwrite a device-originated daily summary with the server's UTC day: around local midnight that stores correct data on yesterday or tomorrow. Accept only strict `YYYY-MM-DD` dates and bounded offsets, test DST/travel/out-of-window cases, and use server time only as a documented fallback when no trustworthy local-day field exists. Keep protocol version, deterministic retry identity, merge metadata, and alias-collision validation on the server; do not require UUIDs, nested dictionaries, or long magic-variable chains merely to compensate for a weak backend contract.
2. Before asking a user to assemble anything beyond a single Health read and POST, perform the earliest possible controlled iPhone POST with one harmless real aggregate against the deployed staging endpoint. Server/unit tests do not prove the exact JSON serialization and magic-variable types emitted by `Get Contents of URL`. If the proof fails, fix and deploy the server adapter first; never add client-side workarounds or expand the Shortcut recipe.
3. Build and validate one action block at a time from the user’s actual Shortcuts screen; action names and available actions vary by iOS release and locale.
3. Before assigning an action, inspect the selected action’s input variable. `Format Date` must consume **Current Date**, never an earlier **Formatted Date** string or the token Text output.
4. Do not assume stock Shortcuts includes a UUID generator. Only if the deployed contract genuinely requires a client UUID, use a verified built-in `Format Date` action with **Current Date** and custom format `yyyyMMdd-HHmm-4ssS-8000-yyyyMMddHHmm`; it matches the UUID version/variant shape without a third-party app.
5. If several formatted outputs are unavoidable, immediately follow each with the stock **Set Variable** action and give it a unique name (for example, `Payload Date` and `Idempotency Key`) before building a Dictionary. Shortcuts otherwise presents indistinguishable `Formatted Date` magic variables and often offers only the nearest one.
6. Keep instructions short and sequential: ask the user to complete the visible action before describing later actions. Give one label-specific correction at a time when the screen differs from the expected action. This prevents accidental duplicated Date actions and miswired magic variables.
7. If the real iPhone request rejects a documented minimal body, stop device assembly immediately and treat it as an endpoint compatibility defect. Reproduce the Shortcuts-compatible request shape without retaining tokens or health values, fix the server, and re-run the one-action device check before giving further build instructions. Do not make the user compensate for a server contract mismatch with more client actions.

## Delivery discipline

- Split delivery into independently reviewable lanes: field-sparse daily-summary ingest, owner-scoped dashboard reads/binding, and Connections visibility/management. After focused reviews, assemble exact immutable commits on current main, run the combined tests/lint/build, push a durable release-candidate ref, and obtain one final combined security review before any deployment. Use staging only when it remains part of the currently authorized release path; if Thomas explicitly waives or retires staging, route the exact reviewed SHA directly through the production guard and do not silently recreate a staging gate.
- Keep dashboard reads authenticated and owner-scoped (`user_id` plus `source = 'apple_health'`); test unauthenticated rejection and cross-user isolation before calling the binding complete.
- Derive morning-versus-evening sync identity server-side from the fields present so two daily automations do not collide under one date, and preserve merge-safe partial updates.
- When reporting status, distinguish four states explicitly: profile/gateway running, task worker running, implementation committed/reviewed, and code deployed. Never use “running” or “done” in a way that implies deployment when the change only exists on a task branch.
- Follow the currently authorized release plan in order. Do not advance beyond an agreed real-device gate until its bounded acceptance checks pass, but do not reintroduce a stage or review lane Thomas has explicitly waived. Encode the active path in task dependencies so stale staging cards cannot block or accidentally release production.
- Treat the bounded Stage 1 gate as: iCloud import plus Import Question substitution, `Find Health Samples` availability, one grouped representative aggregate with `Fill Missing` off, the agreed structured sleep check, and the two automation-run checks. Do not expand this into an exhaustive Health-type catalogue or a screenshot collection.
- Distinguish code assurance from real-device assurance. Synthetic fixtures can approve mappings, aggregation, idempotency, privacy, and visual invariance; only a real device can prove the maintained Shortcut/exporter payload and background behavior. State that remaining evidence gap explicitly rather than blocking an otherwise authorized production release solely because an authenticated test account is unavailable.
- Treat an authenticated endpoint response with `ok: true`, a positive metric-write count, and a receipt as definitive ingest proof. If Connections still says it has not synced, inspect the client-to-API freshness field mapping before asking the user to refresh or rebuild the Shortcut; connection APIs may expose a successful-ingest timestamp under a provider-specific name such as `lastUsedAt`.
- Verify the rendered freshness value after fixing its field mapping. Normalize database timestamps that are stored in UTC without an offset to an explicit UTC instant before browser-side relative-time formatting; otherwise a just-completed sync appears hours old in the user's local timezone. Cover both the provider-specific timestamp fallback and a just-now timezone regression in focused tests.
- When deciding whether the pilot should move from staging to main, compare the actual Wellness and Connections diffs first. A production rollout cannot make a page fuller when the Wellness source is already identical, and an empty production eligibility allow-list keeps the Apple card hidden even if the code is deployed.
- Do not skip device/deployment gates, widen metrics/UI scope, or create a new workflow without approval. When the user says to stay on the staged plan, pause any prematurely started later-stage card immediately rather than reclassifying it as harmless preparation.
- For repeated full-payload syncs, preserve idempotency, null-safe partial merge behavior, later corrections, user isolation, token revocation, and bounded receipt retention.
- When both Wellness and generated exports are stale, diagnose the shared freshness pipeline before narrowing to a UI defect: replay one newer production-shaped payload, then prove the accepted receipt, committed row/date, authenticated API selection, mounted-page update without reopening, and regenerated export all advance to that same observation. Record the first layer that remains stale; byte counts or a successful response alone do not prove that the expected owner/date/metric was selected.
- Audit every Apple metric end to end—exporter label/unit → adapter normalization → `wellness_data` key → owner-scoped API → dashboard key → chart/score input → export field—before fixing a single visible symptom. Canonicalize legacy aliases backward-compatibly, deduplicate equivalent aliases deterministically instead of summing them, define aggregation by metric class, and validate zero per metric because zero activity may be real while zero heart rate, SpO₂, HRV, VO₂ max, weight, or respiratory rate is invalid.
- Treat Health Auto Export as push-only. A POST that arrives after the page's initial GET cannot update mounted state by itself; provide bounded visibility-aware polling or an explicit refresh action, retain known-good values during refresh, tear polling down when hidden/unmounted, and clear loading in `finally` so the UI cannot remain stuck on “Syncing data.”
- Emit privacy-safe success telemetry for exporter ingestion: correlation/event ID, accepted/skipped counts, and structural metric names/units/counts only. Never log values, tokens, user identity, raw dates, source-device names, workout names, or payload bodies. This makes a successful-but-missing Steps upload diagnosable without exposing health data.
- Freeze the approved Wellness composition during pipeline repairs. Keep markup/CSS/card order and disconnected geometry unchanged; require committed pixel baselines across populated, partial, disconnected, loading, stale, and error states at supported phone widths and desktop. Merely writing screenshots is not a visual regression test—compare them against reviewed baselines.
