# Health-data OAuth integrations

## Procedure

1. **Choose the current provider path before coding.** Check the vendor’s official migration and deprecation documentation. Prefer the supported successor API over expanding a legacy device-specific API; health-platform migrations often preserve device access behind a new OAuth surface.
2. **Separate application credentials from user connections.** Store one server-wide client ID, client secret, and exact HTTPS callback for administrators. Give each user Connect, Sync, status, and Disconnect controls without exposing administrator credentials.
3. **Configure OAuth exactly.** Create a Web Server/Web Application client for a server-hosted callback, register the exact production callback including path, add required scopes, and add tester emails while the consent screen is in Testing. Never send client secrets through chat, task cards, logs, screenshots, or memory. Read the callback path and any enable-flag literal from the code first and match them character-for-character across provider registration and host variables — a near-miss path (`/api/health/callback` vs `/api/google-health/callback`) or a wrong flag literal (`true` vs `1`) fails the trial gate with no useful error, so read back every value after setting it.
3b. **Walk a non-technical owner through the provider console one screen at a time.** One step per message, each with the exact clicks and the exact string to type; verify with a screenshot before giving the next step. The owner pastes secrets directly into the host dashboard themselves — the agent names only variable names, never values. Confirm visually (e.g. saved scopes list, test-user table) rather than trusting 'done'.
4. **Test without hardware first.** Prove consent, callback, authorization-code exchange, encrypted token persistence, refresh, disconnect, and empty-data handling with an approved test account. Use the provider’s official mobile app/sample-data or OAuth playground when available; reserve final device-origin verification for real hardware.
5. **Treat client-side health automations as an opt-in connection, not a product mode.** Keep normal app use unchanged; place setup, a narrow per-user ingest credential, status, revocation, and help under Connections. Make the credential write-only and user-scoped, and make each upload idempotent and null-safe so partial or repeated runs never erase valid measurements.
6. **Separate eligibility policy from the per-user Shortcut key.** Broadening Apple Health from a pilot allow-list to every authenticated user removes only the eligibility gate; it must not remove or replace the connection credential. Keep one independently generated/revocable, write-only key per user, hash it at rest, display it once, and scope every upload/read to that owner. Never substitute a shared/global key merely because account access is private.
7. **Preserve an existing health dashboard when that is the requested outcome.** Inspect its current data-loading path before commissioning visual work. If the user wants the existing Wellness page populated, treat its hierarchy and layout as an invariant; extend the source adapter and metric mapping first, use the existing storage model, and do not create an Apple-specific dashboard or redesign by default.
8. **Validate Apple Shortcuts on a real iPhone before committing the server contract.** Build a harmless local fixture first, inspect the actual available Health actions and output shapes, then test a shared iCloud import on a second device. Configure personalization in Shortcut Details → Setup/Import Questions after adding a configurable parameter; it is not an action in the action picker or title menu. An iCloud share link must be created from a Shortcut on an Apple device; do not promise that the server can generate it. Use Import Questions so recipients provide only their own ingest credential. See [Apple Shortcut setup](references/apple-shortcuts-setup.md).
9. **Model status truthfully.** Treat `connected`, `configured`, and `synced` as separate states. A valid OAuth account with no imported measurements is `Account linked; no health data synced yet`, not an error and not proof of successful import. Never fabricate wellness metrics to make the dashboard look populated.
10. **Make management navigation deterministic.** If a dashboard button links to settings with a section query, parse only allowlisted section keys, expand the requested section, focus/scroll it into view, and preserve the state on direct reload. Test the actual deep link, not only the destination page.
11. **Verify authorization boundaries.** Test authenticated administrator and normal-member states across configured, unconfigured, connected, disconnected, and never-synced combinations. Keep server credentials administrator-only while user connection controls remain available where intended.
12. **Release with end-to-end evidence.** Run browser scenarios, build/PWA checks, phone renders, and focused lint/diff checks. After deployment, verify the exact revision, live health endpoint, OAuth redirect behavior, and a real sync response before claiming the integration is publicly ready.
13. **Retire a removed scope end to end, never by silent cleanup.** Bump the consent version, stop requesting and reading the removed scope, update consent text plus privacy-URL default plus every group description and help/error string together, block background sync on legacy broad credentials, rotate or revoke the legacy refresh token through an honest reauthorization path that preserves historical data from retained scopes, and cover both the legacy-token and the new narrow-token path with integration assertions. Sequence owner reauthorization only after the narrow build is deployed: disconnect in app, revoke third-party access on the Google account, then reconnect. Do not claim Google-side selective scope revocation — it is not supported.

## Pitfalls

- Make disconnect/delete fail closed against in-flight authorizations: invalidate all unconsumed pending OAuth states at withdrawal, gate the callback's token commit against a concurrent withdrawal (discard the late token without storing it and revoke it best-effort, queueing on failure), and reset the withdrawal marker only on a fresh explicit start — a stored-token check alone still lets a late callback from an already-open provider page silently reconnect. Cover the legacy-token, narrow-token, successful-revoke, failed-revoke, and late-callback paths with integration assertions, including that a fresh start reconnects normally afterwards.

- Gate trial/proof builds behind a positive staging identity check that fails closed (exact environment/project/service match), never behind the absence of a production flag — an unset NODE_ENV plus an enabled flag must not enable a trial on an unknown host.
- Give PKCE verifiers, pending states, and trial results an independent time-to-live with expired-row cleanup; cleanup that only runs when the next trial starts leaves abandoned rows (and health outcomes) stored indefinitely.
- Enforce per-account trial/start limits atomically at the database level (unique constraint or transaction/lock); a select-then-insert check is bypassed by parallel requests across workers.
- Do not equate an HTTP-healthy service with integration readiness; OAuth configuration and consent verification are external launch gates.
- Do not diagnose “Not synced yet” as a broken connection when no data source exists; inspect token state and sync history separately.
- Do not add a second credential-entry surface for ordinary users; it creates insecure, confusing per-user setup when the server should own app credentials.
- Do not describe Apple Shortcut import questions as an action; Apple exposes them in Shortcut Details → Setup/Import Questions, and the available menu location varies by editor version.
- Do not ask a user to build a full Health shortcut from assumed action names or output types; verify the available Health actions and their real-device result shapes first.
- Do not rely on geometry-only mobile tests for connection management; assert that the correct section is expanded, focused, role-appropriate controls are visible, and status copy matches actual state.
- Do not claim broad public availability from a test-user connection; restricted health scopes may require provider verification or third-party security review before launch.
- Treat a security GO as bound to the exact (SHA, scope-set) pair: widening scopes after a single-scope GO needs a fresh review of the same SHA, never a carry-over of the old verdict.
- When server logs carry no trial lines, accept the user's observed in-app success state as trial evidence and record it on the card — do not hold the gate open waiting for log lines the build never emits.
- Removing a scope's key from stored state does not remove the Google-side grant — the stored refresh token keeps minting access tokens with the original broad permission, so gate the security review on the credential boundary, not only on whether the request path still names the scope.
- When telling a non-technical owner to drop a scope, name the exact scope string to remove under the consent screen's Scopes plus what must stay untouched (API enabled, OAuth client and secrets, redirect URIs, test users) — a vague 'turn it off in the cloud' risks breaking the whole integration.
- Sequence provider-console scope removal with the narrow build's deployment — removing a scope from the console while live code still requests it breaks every new authorization attempt (existing grants keep syncing), so remove and deploy together and reauthorize only after.
- Never retain unused scopes 'for later phases' — every declared scope appears on the user's consent screen and widens provider verification, so request each scope only in the phase that reads it and re-add with a consent-version bump when that phase arrives.
- Scope edits under the consent screen's Data Access tab (never Audience/Clients) are not final until Save — an active unsaved-changes state means removals are still pending, so confirm the saved scope list visually before declaring the console done.
