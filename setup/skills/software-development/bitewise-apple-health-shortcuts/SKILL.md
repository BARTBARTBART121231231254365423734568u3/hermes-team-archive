# BiteWise Apple Health via Shortcuts

## Product boundaries

- Keep normal BiteWise use unchanged. Apple Health is an optional **Settings → Connections** integration available automatically to every existing and future authenticated BiteWise account.
- Do not change the Wellness UI to show Apple-only metrics. Map supported Apple signals only to existing canonical/displayed fields. When a user selects all metrics, skip unknown groups without storing their raw data; add a reviewed canonical mapping first when a new signal is approved for later use.
- Keep account creation and integration eligibility separate: universal Apple Health access does not imply enabling public registration.
- Keep a private key per user even when access is universal. Each signed-in user generates, rotates, and revokes only their own write-only Shortcut credential; store only its hash, reveal plaintext once, and scope every upload to that owner. Never replace this with a shared key, database-read key, or normal account/session token.
- Explain this key as one credential with two inseparable jobs: Bearer authentication proves the sender possesses an active key, and the matching server-side key record selects the owning user for storage. The exporter does not need a separate username. A request appearing in edge/application logs proves only that the public endpoint received network traffic; it does not prove authentication, account routing, validation, or persistence. Report those boundaries separately so “we received it” is never mistaken for “the health data was accepted.”
- Never represent a missing Apple Health value as zero. Preserve missing/unknown values through shortcut payload and server merge behavior.
- Do not assume BiteWise staging exists or recreate it for Apple Health after it has been retired. Use isolated route/integration fixtures for contract proof, then a single guarded production release when Thomas explicitly authorizes direct deployment; reserve real-device production acceptance for the representative observable metric and privacy-safe structural telemetry.
- Before releasing an Apple integration repair through a manifest that targets `main`, verify the reviewed immutable SHA is already the exact remote `main` tip. If it is only on a feature branch, fast-forward/promote that reviewed SHA first, re-fetch to verify the remote ref, and only then start the guarded deploy; otherwise the guard correctly refuses without deploying and wastes a release run.

## End-to-end metric contract and dashboard refresh

Before calling an Apple integration complete, audit every supported metric across the whole contract—not just a single successful Steps sample: exporter/Shortcut label and unit → adapter normalization → `wellness_data.metric_type` → owner-scoped read API → dashboard merge key → card, trend, and score input. Maintain one canonical-key table and test it end to end; a write key such as `calories_out` silently produces an empty card when the dashboard reads only `active_calories` even though upload and storage both succeed.

Make the user's observable representative metric—normally Steps—the release-blocking acceptance path. Prove an iOS-shaped `step_count` payload with multiple observations aggregates into one owner-scoped `wellness_data.steps` row, is returned by the authenticated API, populates both the current-value card and the terminal seven-day point, and appears after the page's bounded post-upload refresh without reopening. Passing adapter, storage, build, or synthetic UI tests separately does not make the integration operational while this visible path still fails. After production, use privacy-safe structural telemetry to confirm the real exporter accepted or skipped `step_count`; distinguish fixture assurance from real-device proof and never describe the feature as operational until the observed metric appears.

Treat Health Auto Export as push-only. A successful upload after the Wellness page's initial GET does not update an already mounted page by itself. Add bounded, visibility-aware polling or an explicit refresh path, stop polling when hidden/unmounted, retain known-good values during refresh, and clear loading in `finally` so one rejected request cannot leave “Syncing health data…” permanently visible.

When the exporter reports success but Wellness remains empty, diagnose the path in strict order: POST status → authentication → accepted/skipped canonical groups → persistence receipt and owner-scoped row counts → connection `last-used` update → authenticated Wellness read API → local-day/freshness/provider selection → dashboard cache/reactivity. A `200` alone can mean the envelope was accepted while every submitted group was unsupported or irrelevant to the visible cards; report accepted canonical categories and persistence separately before touching phone settings. Correlate a named user only from reliable timing or owner-scoped evidence—privacy-safe logs may prove a successful request without identifying its account.

Preserve the device-local day and validated UTC offset from Shortcut/exporter input. Do not assign the server's UTC date to a device-originated daily summary; test local-midnight boundaries, DST changes, and travel offsets because the correct metric can otherwise appear on yesterday or tomorrow.

Define aggregation by metric class before accepting multiple observations for one day: sum additive metrics (steps, energy, distance, exercise/stand minutes, floors), use an explicitly documented bounded rule for physiological samples, and combine sleep sessions/stages without double-counting. Make replay idempotent. Do not reject an entire mixed batch merely because one optional metric is unknown; persist validated supported metrics transactionally. Build success telemetry only from server-owned canonical identifiers: allowlist known metric names/units/reasons, replace every unknown exporter label with bounded placeholders such as `unsupported_metric` / `unsupported_unit`, and record structural accepted/skipped counts without values, raw dates, source labels, tokens, workout names, user identity, or other health PII. Never log an attacker-controlled Health Auto Export `name` or `units` string verbatim, because diagnostics are an exfiltration surface even when health values are omitted.

Validate missing and zero values per metric rather than globally. Zero activity can be legitimate, while zero SpO₂, heart rate, HRV, VO₂ max, weight, or respiratory rate is physiologically invalid and must remain unavailable. Accept only documented/proven aliases and units; convert explicitly (for example kJ to kcal) after finite/range checks instead of guessing.

Apple Health does not provide BiteWise Recovery, Activity, or Sleep scores as a universal native contract. For WHOOP-inspired BiteWise scores, use the public contributor categories and a documented BiteWise-owned calculation—never claim copied proprietary WHOOP weights. Treat HRV statistics as distinct contracts: Apple Health exports SDNN, so persist it as SDNN, compare it only with the user's historical SDNN baseline, and label it explicitly; never store, score, or present SDNN as RMSSD. If another provider supplies RMSSD, keep its series and baseline separate. The visible HRV card may select one valid series deterministically, and dashboard completeness must treat SDNN/RMSSD as alternatives rather than requiring both. Compare current HRV and resting HR against rolling 30-day personal baselines; use sleep hours/efficiency/stages plus baseline-relative respiratory rate, SpO₂, and wrist temperature when available. Require one valid HRV series and resting HR for Recovery; keep a score `—` until at least seven prior valid days exist and display `building baseline` until 30 days are available. For Sleep, derive efficiency only from valid asleep/in-bed totals. For Activity, require steps, active/zone minutes, and active energy; do not silently substitute distance or other context metrics. Expose required inputs, freshness, baseline state, and withheld-score reasons. Verify watch-only metrics with fixtures while clearly separating fixture assurance from real-device proof.

When cards populate but scores remain blank, audit each score independently through a prerequisite matrix: exporter group present → adapter accepted → owner-scoped row persisted → Wellness API field present → Atlas mapping present → score input fresh and valid. Separate today's visible readings from historical baseline coverage: one current HRV and resting-heart-rate card proves only current input, not the minimum count of prior days where both series are valid. Report the valid baseline-day count explicitly before calling Recovery broken; similarly, a `200` upload that accepted only activity groups can legitimately leave Sleep and Recovery blank, and Activity still requires active/exercise minutes in addition to steps and energy. Read current values and trend captions separately: a blank current card with a non-empty seven-day delta proves historical rows exist but does not prove today's reading exists. Treat the card as a selected-day value and the delta as a historical-series summary; never fill the current card with the latest older measurement unless the UI explicitly labels that measurement's date/freshness and score calculations continue using only valid current-day inputs. When one metric from a successful batch renders and another is blank, verify the persisted local day, API key/value type, and current-day selector for each metric before calling it a frontend defect; do not infer that all accepted observations belong to the screen's selected day from one request timestamp. Reproduce the exact API response in both Chromium and WebKit before changing production code; if unchanged production renders it correctly, request one redacted failing-device screenshot and same-session sanitized response shape rather than deploying a speculative mapping fix. Do not assume one blocked historical batch explains every blank score: Sleep and Recovery can legitimately remain unavailable without sleep/HRV history, while Activity should be investigated separately when current steps and active energy already render. Before deploying another compatibility change, prove whether a paused history-parser candidate supplies the missing prerequisites or whether scoring/mapping has its own defect; keep the release paused when the user says to wait.

When multiple providers overlap, select one valid reading deterministically without summing duplicates, but include freshness in the policy so a stale higher-ranked provider cannot hide a fresh Apple reading. Build seven-day trends on contiguous calendar dates and render gaps as missing points rather than compressing available dates together.

For a data-pipeline repair after a Wellness design is approved, freeze that selected UI as a visual contract. Capture populated and disconnected baselines at the supported mobile widths and desktop, then require before/after geometry or pixel evidence proving only legitimate values/status changed—not card order, dimensions, score rings, charts, colors, typography, or empty-state composition.

## Distribution and personalization

- Build and share production shortcuts through Apple Shortcuts/iCloud. Prefer an AI coding agent running on a Mac with Terminal/filesystem access for multi-metric builds: generate or template the `.shortcut`, sign it with Apple’s native `shortcuts sign --mode anyone`, prove the signed file imports, then create the iCloud link. A normal chat-only AI cannot produce or validate the artifact, and an unsigned external file generated on Windows is not a finished deliverable. Distinguish that external file from a Shortcut already installed and edited on an iPhone: the installed copy can run and can normally be shared by iCloud without being re-signed manually. Cherri/HubSign can remotely sign from non-macOS systems, but treat it as an optional third-party path because the complete Shortcut is uploaded to the signing service; never embed the BiteWise key before remote signing. Recipients can install a valid signed file or iCloud link without owning a Mac.
- Add an Import Question for the credential. It is **not** an action in the action search or title dropdown.
- On current iPhone Shortcuts UI: create a configurable Text parameter first; tap the bottom toolbar's circled **i** (Shortcut Details), open Setup/Import Questions, choose that parameter, and set the question text. The iCloud recipient sees it during shortcut configuration.
- Validate installation on a second iPhone using only a synthetic placeholder such as `TEST-ONLY-DO-NOT-USE`; never collect or share real tokens or health data in chat/screenshots.

## Real-device gate

- Verify `Find Health Samples` is available on the target iPhone before committing implementation assumptions.
- The action exposes type, date filters, unit, grouping, sorting, and limiting. Its **Fill Missing** option can insert zeroes; keep it OFF for BiteWise so absent data remains absent.
- Collect only redacted/synthetic payload shapes and action configuration evidence. Do not request actual measurements, Apple IDs, personal shortcut links, or tokens.
- Keep the phone test bounded: prove iCloud import plus Import Question substitution on a second iPhone, confirm `Find Health Samples` and one representative aggregate (Steps), then validate only the small agreed metric set during implementation. Do not make the user catalogue the entire Health-type picker with screenshots; that delays delivery without changing the contract.
- Probe no-sample behavior on the exact target iOS release before designing optional metrics. `Find Health Samples` may raise the system “No Samples Found” error and terminate the Shortcut before a downstream Count/If can run; never claim that `If Count > 0` catches that failure. Do not recommend turning **Fill Missing** on and filtering the resulting zero unless that exact action graph has passed a real-device test proving it reaches the final POST and never serializes the placeholder. Treat absent sleep or optional vitals as missing data, but require a real-device continuation strategy that has been proven to reach the final POST without emitting zero before scaling the Shortcut. If no continuation strategy has passed that test, leave the optional metric out rather than documenting an unverified workaround.
- Test scheduled execution with two temporary Time-of-Day automations created in the **Automation** tab, each set to Run Immediately and targeting the test shortcut. Do not add a `Run Shortcut` action inside the base test shortcut. If the two scheduled Shortcuts notifications appear, accept that as execution proof; iOS may not expose a separate Last Run timestamp.
- Delete temporary test automations and their synthetic test shortcut after proof. Create a clean production shortcut later; never reuse a test artifact with a synthetic placeholder.
- Guide manual Shortcuts work in short sequential chunks with a clear stop point; never hand Thomas an exhaustive multi-action recipe or ask for a catalogue of Health-picker screenshots. Thomas considers even a moderately long hand-built payload flow unacceptable. Use manual construction only for a minimal one-metric device proof; for the complete multi-metric Shortcut, first route generation to an AI coding agent on a Mac with Terminal/filesystem access, use Apple's native `shortcuts sign`, verify real import, and share iCloud links so recipients only enter their own token. Do not start walking Thomas through repeated Count/If/Statistics/Dictionary blocks for every metric. Inspect each supplied screenshot before giving the next instruction, because iPhone Shortcuts placement and labels vary by OS and locale.
- Build dictionary state with an empty **Dictionary** followed by **Set Variable** named `Payload`; do not tell the user to rename the Dictionary action, because that action may not expose a rename control in the current iPhone editor.
- Treat output actions and condition actions as separate only after the Health query itself is proven to return. Leave **Count Items in Health Samples** unchanged, add a distinct **If** below it, select the Count magic variable, then change the If operator to **is greater than** and enter `0`. If the If initially renders as `If Count is Number`, instruct the user to tap the blue `is` operator—not the Count action—to change the comparison. This branch handles an empty returned collection; it does not recover a `Find Health Samples` action that throws and terminates execution.
- Give touch instructions using the exact visible control from the latest screenshot. Never say “tap the empty space” to insert an action; use **Search Actions**, name the action, and then verify or move it between the visible `If` and `Otherwise` markers. Do not call the comparison-condition `+` an action-insertion button unless the current UI visibly proves that behavior.
- Add calculated values and **Set Dictionary Value** actions inside the If branch only, leaving no fallback value in Otherwise, so unavailable Health samples never become fabricated zeroes.
- Before asking Thomas to assemble or rerun a Shortcut, exercise the exact iPhone `Get Contents of URL` JSON/magic-variable representation in a route-level integration test. Do not treat a hand-authored Node JSON fixture as proof that Shortcuts serialization is compatible.
- Classify a live response before proposing any manual edit: `401` indicates credential/header handling, `415` indicates request-body configuration, and a post-auth `422` is server-contract evidence. When a Health Auto Export profile was imported from another phone, a `401` can persist because the imported custom Authorization row retained or malformed its original value even after the visible token was edited. Confirm the POST reached production and failed before payload validation, then delete and recreate the entire header row as `Authorization: Bearer <that account's current bwah_ credential>`; save, fully reopen the exporter, and run one manual send. Never request the credential in chat. If a `422` persists after the visible Shortcut field has been corrected, stop asking Thomas to rewire actions; capture only the sanitized field names/types and response, reproduce that iOS-shaped value in a route-level test, then fix/review/redeploy the server. This prevents retrying manual steps that cannot repair a backend compatibility defect.
- Verify claimed delivery from the production HTTP logs before debugging payload values: look specifically for a `POST` to `/api/integrations/apple-health/v1/daily-metrics` in the run window. A successful connection-key creation or Wellness `GET` proves only account/UI activity; if no ingest `POST` exists, the Shortcut never reached BiteWise, so inspect its final **Get Contents of URL** action and displayed result rather than changing metric aggregation.
- Begin with two daily aggregations after device validation: morning recovery/sleep and late-day activity. Design the server ingest as idempotent and merge-safe so later runs can provide fuller aggregates without erasing earlier valid fields.

## Exporter-app alternative

- When a complete multi-metric Shortcut requires repeated fragile Health-query branches, evaluate a dedicated HealthKit exporter with scheduled REST delivery before asking Thomas to hand-build it. Confirm that REST automation is included in the selected license tier; manual-export/basic tiers do not satisfy unattended sync.
- Keep the exporter pointed away from production while a dedicated adapter is still being designed. Prove its documented JSON shape, metric names, unit labels, authentication header, payload bounds, aggregation, missing-value behavior, and owner-scoped persistence with isolated route tests first. Use a nonproduction environment for device acceptance only when one is intentionally maintained; if staging has been retired, do not recreate it or send personal Health payloads to public request-bin services just to discover the schema.
- Configure Health Auto Export in this order: activate/restore Premium if **REST API** is absent; create **Automations → New Automation → REST API**; enter a staging-only name and endpoint; add `Authorization` with value `Bearer <per-user staging key>`; leave Enabled off until manual acceptance; then choose **Health Metrics**, **JSON**, export **v2**, date range **Today**, **Summarize Data** on, time grouping **Days/Daily**, and batching off for the bounded first test.
- Keep the recurring automation date range on **Today** after acceptance. Seed infrequent readings and score baselines with a separate manual history export: use one bounded **30-day** backfill only for a curated small metric selection; when **All Selected** is enabled, backfill in **7-day chunks** and verify each `200` before continuing, because dense all-metric histories can exceed the request or observation caps. Then return to Today. For Atlas scores, explicitly select **Heart Rate Variability** and **Apple Exercise Time / Exercise Time** in addition to Sleep Analysis, Resting Heart Rate, Steps, and Active Energy: Recovery needs current HRV/RHR plus at least seven prior valid baseline days, Sleep needs duration plus in-bed/efficiency data, and Activity needs steps + active/zone minutes + active energy. VO₂ max is intermittent, so Today-only delivery can legitimately leave it blank even when the connection works. Treat blood oxygen, respiratory rate, distance, and weight as useful signals, not substitutes for those score prerequisites.
- For BiteWise’s approved Health Auto Export pilot, prefer **All Selected** once the production adapter has passed its full-export contract. The server must retain bounded group, observation, and route-specific request limits; authenticate and validate the envelope strictly; store only known canonical metrics; skip structurally valid unknown groups without storing their raw data or exposing their labels/units in logs; and preserve atomic `422` rejection for invalid known metrics. Size the route-specific JSON limit for realistic full exports rather than tiny proof payloads: test one representative valid request above 16 KB through the real HTTP route and persistence path, and test one request above the configured cap still returns `413` before persistence. Keep unrelated/global parser limits unchanged. This lets future server-owned mappings add display/support without making users rebuild their automation: add the reviewed mapping, then ask for one bounded historical backfill. Never use a raw unknown-health cache. Before telling a user to select all, prove a mixed full-export fixture persists exactly supported data, skips unknown groups safely, preserves owner isolation, and still rejects invalid known units/values. Use the full visible label **Walking + Running Distance** when discussing that metric; never shorten it to “Walking,” which is ambiguous among several adjacent metrics.
- Treat a `GET 200` to the Health Auto Export endpoint as URL validation only, not evidence of data delivery. Acceptance requires an observed `POST` and successful owner-scoped persistence. If only GET requests appear, first verify the saved URL includes the full adapter path rather than only the site origin, then use the automation list's visible manual run control; do not change server mappings until a POST reaches the adapter.
- For scheduled-export monitoring, define a bounded observation window and report every new request separately by timestamp, HTTP status, sanitized validation category, and persistence outcome. Privacy-safe production telemetry intentionally may not identify the account; never attribute a request to a named user without a reliable timing or correlation signal. When multiple users may send during the window, label events request A/B and mark attribution uncertain rather than guessing.
- When a real exporter `POST` returns `422` but the app hides the response body, stop changing phone settings blindly. Add a bounded diagnostic that emits a correlation ID and reports only server-owned canonical structure. Allowlist known metric/unit identifiers, replace unknown labels with safe bounded placeholders, and exclude values, dates, source strings, headers, tokens, workout names, and user identity. Run it in nonproduction when available; if staging is intentionally retired and Thomas authorizes direct production diagnosis, deploy it through the normal guard, run one bounded upload, correlate the sanitized event, and remove or retain it according to the approved diagnostics policy.
- Absorb dimensionally equivalent exporter unit drift in the Apple/Health Auto Export adapter rather than making Thomas disable metrics or reconfigure each phone. Normalize case, punctuation, Unicode separators, and whitespace before matching; accept only documented or fixture-proven aliases and convert deterministically after finite/range checks. Examples: `active_energy` may arrive as `kJ` while BiteWise stores kcal; resting heart rate may arrive as `count/min` while BiteWise stores `bpm`; VO₂ max exporters vary among semantically equivalent `mL/kg/min` spellings. Scope aliases to this adapter and canonical metric so Google Health/Fitbit, Garmin, Withings, Strava, provider precedence, and dashboard contracts remain unchanged. Add one mixed-payload regression fixture proving the exporter-shaped batch persists, plus negative tests that dimensionally incompatible units still fail. When privacy-safe telemetry redacts the raw unsupported label, use a safe support channel or a bounded client fixture to prove the alias before broadening it—never weaken validation to accept arbitrary units.
- Treat current/today exports and manual historical-range exports as separate adapter contracts. A small current export can return `200` and persist rows while a larger history export from the same automation returns a pre-transaction `422` because its date representation differs; correlate each POST independently by time, body size, deployment identity, status, and sanitized validation category rather than calling the whole connection fixed or broken. A pre-auth `413` can mask a separate credential failure: after raising a route-specific bounded payload limit, correlate a fresh retry because it may advance to `401`; do not call the phone fixed from the size repair alone. If the header visibly has correct `Bearer ` formatting but fresh requests remain `401`, rotate the account's write-only key and recreate the entire Authorization row because exporter apps may retain an imported or stale value despite the visible field. When the category is `date`, adapt only the Apple/Health Auto Export parser to normalize fixture-proven date-only, device-local, and standard ISO-offset forms into the existing local-day contract. Preserve the supplied device-local calendar day, reject impossible dates and ambiguous locale strings, prevent timezone conversion from shifting the day, keep raw dates out of telemetry, and add both current-export and historical-range fixtures plus invalid-date, atomicity, and owner-isolation tests. Do not change Google Health/Fitbit or other provider date contracts to accommodate an Apple exporter variant.
- Reuse the existing per-user write-only Bearer credential for exporter apps. Never embed a shared key, expose the key in screenshots, or infer successful ingestion from a key-creation request or dashboard GET; verify the exporter POST and resulting owner-scoped rows separately. Treat even a partially visible credential as exposed: rotate it after the current bounded diagnostic run, then update the exporter privately before further testing.
- Account for iOS HealthKit background restrictions in acceptance criteria: scheduled exporter jobs may be delayed while the device is locked, inactive, in Low Power Mode, or denied Background App Refresh. Require a manual staging send first, then prove background behavior on the target phone before presenting it as reliable automation.
- When a release follow-up reports one concrete defect, review and re-test only that defect plus its immediate regression surface; do not restart the entire previously approved pipeline. If an emergency rollback makes `main` diverge from the approved candidate, preserve history by creating a one-commit descendant of rollback `main` whose complete tree equals the approved release tree, then review ancestry and tree equality only before deploying the integration SHA. Never force-push or reopen broad implementation review merely to reconcile ancestry.
- Close real-device staging acceptance only after the exact deployed SHA is SUCCESS/RUNNING and a normal iPhone run produces an authenticated `POST` with HTTP 200. For narrow follow-up defects, review only the newly changed contract and its immediate regression surface; do not restart a whole-feature review chain or create redundant review cards when an exact-SHA independent approval already covers the unchanged implementation. Health Auto Export may issue more than one POST for a single manual run, so make ingestion transactional and idempotent rather than treating duplicate successful requests as an error. Record only status, request timing, deployment identity, and metric counts—never health values. Promote that same immutable SHA to production, then replace both the staging URL and staging key with a newly generated production URL/key; do not assume credentials cross environments.
- Coach phone configuration one visible screen at a time. Name the exact tappable row or toggle shown in the latest screenshot, give only the next small block, and stop for visual confirmation before fields containing credentials can re-enter view; this prevents vague gestures and accidental key exposure. Treat every screenshot as device-scoped evidence: confirm which account/phone it belongs to before correlating it with production logs, and immediately correct the active investigation when Thomas switches the named user. For Authorization screenshots, inspect the delimiter itself—`Bearer` must be followed by exactly one space—but never repeat the credential in chat. Distinguish **Enabled** from manual delivery: an off automation toggle explains missing scheduled exports, not a `401` from a manual POST that already reached BiteWise. Require **Update/Save**, a full app reopen, and one bounded manual send before reading the newest sanitized production status.

## Parallel delivery and evidence

- Separate the device-only gate from code assurance: let implementation and independent server/security review proceed against synthetic fixtures while the maintained iCloud shortcut artifact, redacted output matrix, and scheduled-automation evidence await a physical iPhone. Never invent those device artifacts.
- Treat the final shared iCloud shortcut link and automation-run proof as manual acceptance evidence, not as a reason to weaken endpoint validation, token isolation, rate limits, or server tests.
