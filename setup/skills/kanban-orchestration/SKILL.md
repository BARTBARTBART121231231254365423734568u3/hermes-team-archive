# Kanban Orchestration

Run multi-worker delivery through the shared board so the owner never chases agents.

## Card quality

- Write COMPLETE task bodies. Never abbreviate with truncation markers or 'see previous' — workers treat the body as ground truth and a cut body causes blocks and rework.
- Put every decision the worker depends on IN the body (naming, schemas, branch, base SHA, scope limits); workers cannot see sibling context. Read the stored card and comments back after creation: a successful write can persist a literal truncation marker, so split lengthy corrective context into short complete comments and verify each critical SHA/path rather than repeatedly posting longer corrections.
- Check open cards before creating to avoid duplicates; use idempotency keys for retry-safe creation.
- Set an explicit non-zero priority on every card you create — the dispatcher serves the highest priority first, so a priority-0 review or rework card queues behind all other work for that profile and reads as stalled. Mirror the lane's urgency (rework and re-reviews near the original build priority).
- When the owner requires the worker to fan out internally (subagents/delegate_task), the coordinator cannot observe that fan-out — so make it verifiable on the card: require the worker to report which subagents run with what scope in its first heartbeat/comment. A silent solo run after such an instruction is a steering failure, not a worker preference. If the worker reports delegation is technically impossible (tool missing/errors) or keeps working solo, split the work at board level into parallel child cards with disjoint file scopes instead of repeating the instruction.

## Model routing per card

- When one job must run on a different provider or model, pin `model` + `provider` overrides on that card at creation — never rewrite every profile's primary for a single job. Bulk profile edits are disruptive, hard to verify, and the owner will stop you mid-way.
- A `fallback_providers` entry is not a way to run work on that model: it fires only when the primary fails, so a healthy primary means the fallback never runs. "Run everything on X" always means changing primaries or per-card overrides, never just setting a fallback.
- Read back `model_override`/`provider_override` like any other critical field — a typo'd override fails at dispatch, not at creation, so creation success alone proves nothing.
- Never tell the owner which model powers the live session from memory — read the run-linked routing event. A session keeps its spawn-time routing and never switches mid-flight, so a pre-change session still runs the old model.

## Sequencing

- Express dependencies with `parents`/`kanban_link`, not prose. Work that touches the same files runs sequentially (fix → fix → gates); independent work runs parallel within team limits.
- Never split a card into sub-cards without the owner's explicit permission — one card, one worker, unless the owner approved the split. If a split already exists when the owner forbids it, park the extra card with a do-not-pick-up comment and route all remaining work through the original card.
- After merging new work to the base branch, rebase (or explicitly confirm the base of) every dependent task worktree before unblocking it — a worktree whose branch no longer contains the repository HEAD fails preflight and crash-loops instead of working.
- When rebase or force-push is forbidden, merge the base branch into the task branch instead — preflight only requires the branch to contain the repository HEAD, and a forward merge satisfies that without rewriting history.
- After a policy-denied chained shell command, re-read branch, log, and status before acting — the whole chain is rejected pre-execution, so assume none of its steps ran until the read proves otherwise.
- Never resolve conflicts or commit/stash inside a worker-owned worktree yourself — if a repair merge aborts on conflict, leave staged and untracked work untouched, post the exact merge command as a card comment, and unblock so the worker resolves in its own context.
- When a diagnosis becomes a request to fix, turn it into implementation → independent review → activation → live verification; read back each card's exact scope and dependency path, then confirm that the implementer is actually claimed. If capacity leaves it queued, state that limitation plainly and do not present the queued chain as a completed fix or promise unattended follow-through without a verified trigger.
- When the owner asks to optimize coder throughput *after* an in-flight release, first finish its review, activation and live verification. Gate a read-only bottleneck analysis behind that verified result instead of competing for scarce worker slots during the release; before assigning it, inspect the target profile's enabled local file/terminal tools so it can actually query the board and worker logs. Measure parent-gated `todo` separately from runnable `ready`, ready-to-claim, run duration, provider errors, rework and delegated-child join time, then propose a few bounded experiments with baseline, safety gates and rollback. Do not infer that every queued card needs another coder slot, or change Thomas's manually chosen coder model as an optimization.
- When the request is bulk work against external sources (imports, scrapes, bulk enrichment), sequence it as spike → contract → build: the spike verifies extraction on one real item PER source, records a per-source terms/robots assessment (whether automated extraction AND reuse are permitted, and under what license), measures what existing providers already cover on a same-size sample, and delivers a small pilot dataset plus an effort estimate; the implementation contract is a separate card with the spike as parent and uses only the spike handoff as its source. On an explicit source prohibition the spike blocks as needs_input with the cited terms instead of building the pilot; an owner decision to proceed anyway is recorded as a dated comment with explicit mitigations (facts only, no media or creative texts, polite rate, per-item attribution) before unblocking. Scoping bulk effort from one verified source while assuming the others match produces contracts a coder cannot execute. An active technical access-denial (HTTP 403, WAF/bot-wall on every request) is a separate gate from a terms prohibition: never order its circumvention (alternate egress, stealth tooling, session spoofing) on the back of a prior scraping approval — put the explicit choice (legal access route, owner-authorized circumvention with owner-held risk, or park the source) to the owner and record it before unblocking. Vague workaround language is not authorization; clarify it into one of those options first. When existing-provider coverage on the pilot sample is high, contract the coverage-first-plus-gap-fill variant as the recommended path and let the owner decide whether the residual bulk is worth its runtime and risk before building.
- When an auto-decomposed child (or any card) fails preflight for a missing workspace/repo anchor, repair the existing executable lane and its parent graph before retrying. Recreate only when the original cannot be repaired, with an explicit verified repo-anchored workspace and a complete body; a blind retry replays the same preflight failure.
- When a card's only deliverable already exists in durable form (parent comments, screenshots, metadata), the coordinator may complete it with a summary + metadata pointing at that evidence instead of dispatching another worker round — prefer this over re-dispatch when no new work exists.
- When the owner reverses scope mid-flight (a decided approach is replaced while cards run), annotate the running card with a dated scope-change comment stating what still applies and what no longer does, rewrite only the not-yet-started children to the new direction, and leave sound running work intact — rebuilding a running lane on the new decision wastes the round, and stale cards silently execute the old one.
- Before merging a worker branch into the base, confirm the base HEAD is an ancestor of the branch (`git merge-base --is-ancestor`); merge with `--no-ff` naming the worker commit and its evidence (test counts), push, then confirm the live revision — the merge succeeding locally proves nothing about what deployed. When the failures are repeated worker spawn crashes (not task content) and the stranded worktree holds sound prior work, the approach-change may be to finish the remaining delta directly: inspect the worktree state, implement only what is missing in the task branch, run the package verify, merge, and complete with evidence — instead of respawning the same crash.
- Before turning a scoped local release into a full-suite or hosted-CI repair project, establish which gate is truly required and run the release-risk matrix against the exact candidate plus an unchanged baseline. If unrelated baseline failures keep surfacing, stop the repair cascade: preserve the release block, present the owner one bounded choice between keeping the original gate and explicitly accepting a version-bound exception, and require independent code/security and guarded operator checks either way. Silence never waives a gate.
- Before touching a task-owned checkout to correct a stale base, read its live claim/run state as well as Git status and branch. Never reset or switch it once a worker has claimed it without coordinating that worker; changing HEAD concurrently invalidates its preflight assumptions.
- When a review returns NO-GO, record a reproducible failing behavior and create one bounded rework card on the exact candidate SHA. Before it becomes claimable, resolve the project in the creating profile, omit `workspace_path` for a project-linked worktree, then read back its non-null project ID, canonical task-owned path, branch, base and parent links; review-created children do not inherit repository authority merely from `creator_task_id`. Link rework as a parent of the existing review so release stays gated until the correction receives a fresh GO and any required owner sign-off. When the rework lands on a new SHA, open fresh review cards bound to that exact SHA instead of recycling the NO-GO card — verdicts bind per SHA, so the old card keeps its immutable NO-GO while the new cards carry the new candidate SHA, the new base SHA, and the expected changed-file set, with a real priority so the re-verdict does not stall behind unrelated work.

## Owner decisions and conversation routing

- When a project worker needs a material owner choice, investigate existing approvals and bundle only the genuinely missing choices with a recommended option; a `needs_input` block is a coordinator handoff, not permission to leave the owner chasing the board. For external-account access, distinguish a one-time owner login from persistent agent credentials and verify the effective identity and project scope. If the owner explicitly chooses an existing account and rejects a speculative broader-access concern, stop re-arguing the rejected risk: accept the chosen identity, constrain the requested OAuth scopes and agent tools to the authorized project, check effective access when authenticated, and ask again only if the check proves a material mismatch. Record the exact project identifier and chosen auth boundary on the active handoff before changing IAM or credentials.
- When proposing paid model or provider usage, justify it function by function — which functions need the heavier tier and concretely why the light default fails them — with per-unit cost math at the expected volume, and default to the lightest tier that passes. A flat request for the strong model without that breakdown gets rejected; the breakdown is the proposal.
- When a card blocks repeatedly because owner answers arrived scattered across cards and comments, write ONE consolidated decision comment on the blocked card itself that explicitly supersedes all partials, then unblock — re-unblocking with fragmented context replays the same block.
- Record a standing owner authorization (e.g. overnight blanket approval to proceed without check-ins) as a dated comment on the active card with explicit exclusions — what it covers and what still needs per-case approval (production releases, new costs, out-of-scope work, external publication). Standing approval never waives those gates. Record a conditional approval the same way — the exact trigger (which gate verdicts release which action) and what still needs a fresh decision — then execute the trigger without re-asking when it fires.
- When a card blocks twice on missing worker capabilities (no file tools, no local access) rather than task content, stop unblocking: reroute to a tool-capable profile or narrow the card to what its tools can actually reach.
- Ask project-specific questions in that project's originating conversation, not in an unrelated diagnostic chat. Confirm that the question was actually delivered there; a board comment or queued card is not a delivered request. Never inject a coordinator instruction through a resumed session as if it were a new user message, because the forged role can be mistaken for owner authorization. If the origin cannot be reached with a verified route, keep the sensitive lane blocked and state the routing limitation without moving the question into the wrong chat.

## Verification before reporting

- Re-verify worker claims independently (tests, logs, live endpoints, screenshots) before telling the owner anything is done. When an owner forwards a truncated completion notification, read the full run verdict and metadata before treating its opening line as approval; the omitted portion may contain a binding caveat.
- At a multi-review release fan-in, compare each verdict's exact candidate SHA and evidence. If one reviewer approves statically but cannot run tests, preserve that as a conditional GO, point the activation worker to the other reviewer's exact-SHA test evidence, and require its own targeted validation (plus any mandatory CI) before changing live config. A review card marked `done` does not by itself satisfy a test or activation gate.
- For user-facing status during a guarded release, distinguish `ready` from claimed/running, local code GO from operator-package GO, and both from the installed runtime plus live interaction proof. Check the installed revision and active worker count before the answer; lead with `not live` when that is the result instead of reciting intermediate GO notices. If a worker cannot safely restart its own gateway, verify the operator's process cgroup differs from the gateway service cgroup, then use that independently scoped interactive operator only after productive workers drain and approval is bound to the exact revision. Run the package's read-only preflight with its tested interpreter; evaluate that command's own exit and PASS/FAIL output, not a later command's exit in a chained shell. Do not relabel preparation as activation or promise unattended follow-up without an actual trigger.
- Never call an untested connector, native app, or release 'done'. Report `built` and `tested` as separate states with evidence links.
- Before unblocking an approved release, read the installed runtime's actual revision (symlink/checkout and process-state fingerprint where available) and compare it with the reviewed candidate's base/ancestry. Concurrent work may advance the runtime after Security GO; integrate the candidate onto that exact live base, rerun focused tests and independent exact-head review instead of activating an older branch that replaces newer fixes. Keep an existing operator/capability gate blocked until its actual prerequisite is resolved; code GO does not release that gate.
- After any push that should deploy, confirm the exact live revision and behavior (deployment status + live endpoint), not just the push.
- Inspect the worker's own visual evidence yourself (open the screenshots) before presenting it to the owner — independent review passes still miss visible defects like raw internal IDs rendered in the UI.
- When the owner rejects visuals as slop, stop defending the work; re-deliver the comparison with every visible difference labeled (test data vs deliberate simplification vs real bug) so they only judge the bugs.

## Infra first

- A worker crash-loop with `No space left on device` (or repeated spawn failures) is an infra problem, not a task problem: check disk/quota/credentials first, park the cards, fix infra, then resume.
- Quota/rate-limit exhaustion on all provider entries means waiting or new credentials — not rerouting the same model.
